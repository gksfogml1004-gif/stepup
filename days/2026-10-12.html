💡개념 — JVM 메모리는 어디에 무엇을 두나
1Stack
메서드 호출·지역 변수·객체의 주소(참조)스레드마다 따로 · 메서드가 끝나면 자동 정리
넘치면 StackOverflowError
2Heap
new로 만든 객체 자체모든 스레드가 공유 · GC가 정리하는 곳
부족하면 OutOfMemoryError: Java heap space
3Metaspace
클래스 정보, static 영역Java 8부터 (이전엔 PermGen)
재배포를 반복하면 늘어날 수 있음
4GC
더 이상 참조되지 않는 객체를 자동으로 치움정리하는 동안 앱이 잠깐 멈출 수 있음
(Stop-The-World)
📌 Order o = new Order(); → 객체는 Heap에, 변수 o에는 그 객체의 주소만 Stack에 담깁니다. 아무 변수도 그 주소를 들고 있지 않으면 GC 대상이 돼요.

메모리 에러 메시지별로 원인이 다릅니다

Java heap space
객체가 너무 많거나 안 치워짐
→ 대량 조회, 메모리 누수 의심
Metaspace
클래스 정보 영역 부족
→ 재기동 없이 재배포 반복, 라이브러리 과다
StackOverflowError
호출이 너무 깊음
→ 끝나지 않는 재귀 호출 의심
🔬 심화 — 더 깊이 보기 (+5분)
① 세대별(Generational) GC — 대부분의 객체는 금방 죽는다Heap은 Young(Eden + Survivor)과 Old로 나뉩니다. 새 객체는 Eden에 생기고, 여러 번 살아남으면 Old로 옮겨져요. Young 정리(Minor GC)는 자주·짧게, Old까지 정리하는 Full GC는 드물지만 길게 멈춥니다. "화면이 몇 초씩 멈춰요"의 흔한 원인이 Full GC 반복이에요.
② 메모리를 늘리는 게 정답이 아닌 경우메모리 누수(static 컬렉션에 계속 쌓기, 닫지 않은 자원 등)라면 -Xmx를 늘려도 OOM이 늦게 올 뿐이고, 오히려 Full GC 한 번이 더 길어집니다. GC 직후 사용량이 계단처럼 계속 올라가면 누수, 특정 기능 실행 때만 치솟으면 대량 조회를 의심하세요.
③ 버전·WAS별로 다른 점Java 8은 기본 GC가 Parallel, Java 9부터는 G1이 기본입니다. 힙 옵션은 Tomcat이면 bin/setenv.sh의 CATALINA_OPTS, JEUS 같은 상용 WAS는 관리 콘솔·도메인 설정의 JVM 옵션 항목에 넣어요.
# Tomcat 예시: bin/setenv.sh
CATALINA_OPTS="-Xms2g -Xmx2g
  -XX:+HeapDumpOnOutOfMemoryError
  -XX:HeapDumpPath=/app/dump"
④ 리뷰·면접에서 나오는 질문Q. 운영 서버에서 -Xms와 -Xmx를 같은 값으로 주는 이유는?
A. 힙이 커졌다 줄었다 하는 비용과 그때 생기는 GC를 없애 성능을 안정적으로 만들기 위해서입니다. 대신 서버 물리 메모리와 다른 프로세스 사용량을 고려해 정해야 해요.
🔍실습 1 · 지금 JVM 옵션 확인
# 실행 중인 Java 프로세스와 옵션
ps -ef | grep java
# 실제 적용된 JVM 플래그 (JVM과 같은 사용자로)
jcmd <pid> VM.flags
▶ 이렇게 나오면
appuser 2310 1 5 09:01 ? 00:12:31 /usr/lib/jvm/java-11/bin/java
  -Xms2g -Xmx2g -XX:+UseG1GC
  -Dcatalina.base=/app/tomcat ...
🔎 결과 읽는 법
  • -Xmx가 최대 힙, -Xms가 시작 힙이에요
  • 옵션이 없으면 JVM이 서버 메모리 기준으로 자동으로 정해요(보통 물리 메모리의 1/4)
  • 한 서버에 WAS가 여러 개면 힙 합계 + OS 여유분이 물리 메모리를 넘지 않는지 free -h로 비교
📈실습 2 · GC 상황 실시간으로 보기
# 1초 간격으로 5번 출력
jstat -gcutil <pid> 1000 5
▶ 이렇게 나오면
  S0    S1     E      O      M    CCS   YGC   YGCT  FGC  FGCT  CGC  CGCT    GCT
 0.00 45.12  63.80  71.25  95.10 92.33  1520 12.345    8 3.210    0 0.000 15.555
🔎 결과 읽는 법
  • E(Eden)·O(Old)·M(Metaspace)은 사용률(%), YGC/FGC는 Young/Full GC 누적 횟수예요
  • O가 GC 후에도 90% 이상에 머물고 FGC가 짧은 간격으로 계속 늘면 위험 신호(멈춤의 원인)
  • YGC가 자주 느는 건 정상이에요. 판단은 FGC와 Old 추이로
  • 열 구성은 Java 버전에 따라 조금 달라요(위는 Java 11 기준)
🧯실습 3 · 장애 때 증거 남기기 (덤프)
# 스레드 덤프: 멈춤·지연 원인 확인 (가벼움)
jcmd <pid> Thread.print > /app/dump/thread_$(date +%H%M%S).txt
# 힙 덤프: 무엇이 메모리를 차지하나 (무거움)
jmap -dump:live,format=b,file=/app/dump/heap.hprof <pid>
▶ 이렇게 나오면
Dumping heap to /app/dump/heap.hprof ...
Heap dump file created
🔎 결과 읽는 법
  • 스레드 덤프는 몇 초 간격으로 2~3번 떠야 "계속 같은 곳에 멈춰 있는지" 비교할 수 있어요
  • 힙 덤프는 힙 크기만큼 디스크가 필요하고, live 옵션은 덤프 전 Full GC를 일으켜 잠깐 멈춥니다
  • 힙 덤프 분석은 Eclipse MAT 같은 도구로 "가장 큰 객체"부터 봅니다
  • jcmd·jmap은 JVM을 실행한 같은 사용자로 실행해야 붙어요
⚠️ 운영 중 힙 덤프는 서비스가 잠시 멈출 수 있어요. 가능하면 사전 공지하고, 평소엔 -XX:+HeapDumpOnOutOfMemoryError로 자동 덤프를 걸어 두세요.
⚠️흔한 실수현장에서 실제로 자주 나오는 것
  • OOM이 나자마자 -Xmx만 올리고 종료원인(누수·대량 조회)이 그대로라 며칠 뒤 다시 납니다. 늘리더라도 원인 분석을 함께 진행하세요.
  • 재기동부터 해서 증거가 사라짐재기동하면 메모리 상태가 날아갑니다. 서비스 복구가 급해도 스레드 덤프 1~2개와 로그 확보는 1분이면 됩니다.
  • 서버 메모리보다 큰 힙 합계WAS 여러 개의 힙을 합치면 물리 메모리를 넘는 경우가 있어요. 스왑이 생겨 전체가 느려지거나, OS가 프로세스를 강제로 종료할 수 있습니다.
  • 대량 데이터를 List에 통째로 담기엑셀 다운로드에서 수십만 건을 한 번에 조회하는 게 대표적인 OOM 원인이에요. 페이징, 스트리밍 처리(MyBatis ResultHandler, fetchSize)를 검토하세요.
🧾실무 팁 (SM 관점)
  • 운영 WAS에는 OOM 시 자동 힙 덤프 옵션과 덤프 경로(디스크 여유 있는 곳)를 미리 설정
  • GC 로그를 남겨 두면 사후 분석이 가능해요 — Java 9+: -Xlog:gc*:file=/app/logs/gc.log
  • 장애보고서엔 "메모리 부족" 대신 영역(Heap/Metaspace)·기능·데이터 건수를 구체적으로
  • 정기점검 항목에 Old 사용률 추이와 Full GC 횟수를 넣으면 장애 전에 징후를 잡을 수 있어요
✏️오늘의 퀴즈정답 확인 후 알았음/헷갈림 표시

Q1. 메서드 안에서 Order o = new Order();를 실행했다. 변수 o와 Order 객체는 각각 어디에 있을까?

정답
변수 o(주소)는 Stack, Order 객체는 Heap에 있습니다.

Q2. jstat을 보니 O(Old)가 99%이고 FGC가 1분마다 늘어난다. 무슨 상황이고 무엇을 해야 할까?

정답
Full GC를 해도 Old가 비워지지 않는 상태 → 누수나 과다 적재 의심. 스레드·힙 덤프와 로그를 확보하고 원인 기능을 찾습니다.

Q3. -Xmx를 2배로 늘렸는데 며칠 뒤 또 OOM이 났다. 가장 먼저 의심할 것은?

정답
메모리 누수. 늘린 만큼 늦게 왔을 뿐이에요. GC 후 사용량이 계속 올라가는지 확인하고 힙 덤프로 쌓이는 객체를 찾습니다.

Q4. 화면이 멈춰서 WAS를 재기동하려 한다. 재기동 전에 꼭 남겨야 할 것은?

정답
스레드 덤프(2~3회), 에러·GC 로그, 가능하면 힙 덤프. 재기동하면 원인 증거가 사라집니다.

✍️문제 1쉬움

Java에서 new로 생성한 객체가 저장되는 메모리 영역은?

정답 2번. 객체는 힙에 생성되고, 그 객체를 가리키는 지역 변수(참조)는 스택에 저장됩니다.
✍️문제 2보통

JVM 메모리 영역 중 모든 스레드가 공유하는 영역으로만 묶인 것은?

정답 2번. 힙과 메서드 영역은 공유, 스택·PC 레지스터·네이티브 메서드 스택은 스레드마다 따로 생깁니다.
✍️문제 3함정

가비지 컬렉션(GC)에 대한 설명으로 틀린 것은?

정답 2번. System.gc()는 GC를 요청할 뿐, 즉시 수행을 보장하지 않습니다(JVM 판단·옵션에 따라 무시될 수도 있음). 운영 코드에서 호출하는 건 권장되지 않아요.

📍 WAS 에러 로그

memory leak
메모리 누수
📍 장애 분석·이슈 트래커
The heap usage keeps growing after each GC, which suggests a memory leak.GC 후에도 힙 사용량이 계속 늘어나 메모리 누수가 의심된다.
GC pause
GC로 인한 멈춤
📍 GC 로그·성능 문서
Long GC pauses caused request timeouts.긴 GC 멈춤 때문에 요청 시간 초과가 발생했다.
heap dump / thread dump
힙 덤프 / 스레드 덤프
📍 장애 대응 절차서
Take a thread dump before restarting the server.서버를 재기동하기 전에 스레드 덤프를 떠 두세요.

스택 트레이스 (호출 경로)
📍 에러 로그·이슈 보고

💡 스택 트레이스는 위가 가장 최근 호출, 아래로 갈수록 호출한 쪽이에요. 단, OOM은 "마지막으로 메모리를 요청한 곳"에서 터질 뿐 진짜 범인이 다른 곳일 수 있어서 힙 덤프로 확인하는 게 정석입니다.
JVM
Java Virtual Machine. 자바 바이트코드를 실행하고 메모리·GC를 관리하는 실행 환경
힙 (Heap)
new로 만든 객체가 저장되는 JVM 메모리 영역. 모든 스레드가 공유하며 GC 대상
스택 (Stack)
메서드 호출 정보와 지역 변수(객체 주소 포함)를 담는 스레드별 메모리 영역
Metaspace
클래스 정보·static 등을 담는 영역. Java 8부터 PermGen을 대체
GC (Garbage Collection)
더 이상 참조되지 않는 객체를 자동으로 회수하는 JVM 기능
Stop-The-World
GC 중 애플리케이션 스레드가 잠시 멈추는 현상
Full GC
Old 영역까지 포함해 힙 전체를 정리하는 GC. 오래 멈출 수 있음
메모리 누수 (Memory Leak)
쓰지 않는 객체가 계속 참조되어 GC가 회수하지 못하고 쌓이는 현상
힙 덤프 (Heap Dump)
특정 시점의 힙 메모리 내용을 파일로 저장한 것. 메모리 원인 분석용
스레드 덤프 (Thread Dump)
모든 스레드가 그 순간 무엇을 하고 있는지 출력한 것. 멈춤·지연 분석용
