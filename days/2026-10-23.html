같은 장애, 원인 문장 비교

사람 탓
"작업자 실수로 2호기 배포 누락"
→ 다음엔 "더 주의" 말고 할 게 없음
구조 탓
"배포 절차에 전 노드 버전 확인 단계가 없어 2호기 누락을 발견하지 못함"
→ 고칠 대상이 보임
직접 vs 근본 원인
직접: 2호기가 옛 버전으로 동작
근본: 배포 후 검증 절차 부재
🔬 심화 — 더 깊이 보기 (+5분)
① 5 Whys — "왜?"를 다섯 번간헐적 주문 오류 → 왜? 2호기만 오류 → 왜? 2호기가 옛 버전 → 왜? 2호기 배포가 빠짐 → 왜? 수동 배포를 1호기만 하고 끝냄 → 왜? 절차서에 노드별 확인 단계가 없음. 마지막 "왜"에서 나온 것이 근본 원인이고, 재발 방지는 여기를 고쳐요.
② 숫자로 말하는 장애 — MTTD · MTTRMTTD(발생→인지까지 걸린 시간)와 MTTR(인지→복구까지 걸린 시간)을 적으면, "알람이 늦었는지"와 "복구가 늦었는지"가 구분돼요. 월간 운영보고서의 SLA 지표(10/09)와도 연결됩니다.
③ 비난 없는 회고(Blameless)보고서에 개인 이름·책임 추궁 문구가 들어가면 다음 장애 때 사람들이 사실을 숨기게 돼요. 역할(작업자, 확인자)로 쓰고, 개선 대상을 절차·도구·알람으로 잡는 게 원칙입니다. 계약상 책임 소재가 필요한 경우엔 별도 문서로 분리하는 편이 좋아요.
④ 리뷰·면접에서 나오는 질문Q. 장애보고서에서 가장 중요한 항목은?
A. 재발 방지 대책이요. 그것도 "주의하겠다"가 아니라 무엇을 바꾸는지, 담당, 기한, 완료 확인 방법이 있어야 실행됩니다.
📄실습 1 · 장애보고서 양식 (케이스 스터디로 채운 예)
# 장애보고서
제목   : 주문 API 간헐 오류 (WAS 2호기 배포 누락)
일시   : 2026-10-23 09:02 ~ 09:48 (46분, KST)
영향   : 주문 요청의 약 50% 실패 (예시 수치)
인지   : 09:02 오류율 알람 / 복구 09:48
직접원인: WAS 2호기가 이전 버전으로 동작
근본원인: 배포 절차에 노드별 버전 확인 단계 없음
조치   : 2호기 LB 제외(09:31) → 재배포 → 투입(09:48)
재발방지: ① 배포 체크리스트에 전 노드 md5 비교
           (운영 담당, 10/30까지)
         ② 배포 후 노드별 헬스체크 URL 확인 자동화
           (개발 담당, 11/13까지)
🔎 결과 읽는 법
  • 일시·영향은 숫자로 — 몇 분, 몇 %, 어떤 업무
  • 직접 원인과 근본 원인을 따로 써야 재발 방지가 근본을 향해요
  • 재발 방지마다 담당·기한이 있어야 다음 달 점검 때 완료 여부를 확인할 수 있어요
⏱️실습 2 · 로그로 타임라인 뽑기
# 두 WAS 로그를 시간순으로 합쳐 보기
grep -h "ERROR" was1/app.log was2/app.log \
  | sort | head -5
# 서버별 에러 건수 비교
grep -c "ERROR" was1/app.log was2/app.log
▶ 이렇게 나오면
2026-10-23 09:01:58 ERROR [exec-3] OrderController - NoSuchMethodError
2026-10-23 09:02:01 ERROR [exec-9] OrderController - NoSuchMethodError
...
was1/app.log:0
was2/app.log:1873
🔎 결과 읽는 법
  • -h는 파일명 없이 출력 → sort로 시간순 합치기(로그 앞이 시각일 때)
  • was1 0건 / was2 1,873건 → 2호기만의 문제라는 결정적 근거
  • NoSuchMethodError는 서로 다른 버전의 클래스가 섞였을 때 자주 나요
🔁실습 3 · 5 Whys 적어 보기
  • 왜 주문이 가끔 실패했나? → 요청의 절반이 가는 2호기에서만 오류
  • 왜 2호기만? → 2호기가 이전 버전 파일로 동작
  • 왜 이전 버전? → 수동 배포를 1호기만 하고 종료
  • 왜 몰랐나? → 배포 후 확인을 대표 URL 1건으로만 함 (LB가 1호기로 보냄)
  • 왜 그렇게 했나? → 절차서에 노드별 확인 단계가 없음 ← 근본 원인
💡 "왜"의 답이 사람(실수·부주의)에서 멈추면 한 번 더 물어보세요. 그 실수를 막지 못한 절차·도구가 나옵니다.
✅좋은 재발 방지 체크
  • 무엇을: 체크리스트 항목 추가, 자동화, 알람 기준 변경 등 바꿀 대상이 구체적인가
  • 누가: 담당(역할)이 정해졌나
  • 언제까지: 기한이 있나
  • 확인: 끝났는지 어떻게 확인하나 (다음 배포 결과서에 md5 비교 첨부 등)
  • 나쁜 예: "작업 시 주의 철저", "교육 강화"만 있는 경우
⚠️흔한 실수현장에서 실제로 자주 나오는 것
  • 원인에 "작업자 실수"만사람은 또 실수해요. 실수를 막지 못한 절차·도구를 원인으로 적어야 고칠 수 있어요.
  • 타임라인을 기억으로 작성시각이 틀리면 MTTD·MTTR도 틀려요. 로그·알람·메신저 시각으로 적으세요.
  • 재발 방지에 담당·기한 없음"검토하겠다"는 아무도 하지 않아요. 역할과 날짜를 붙이세요.
  • 영향 범위를 모호하게"일부 사용자 불편" 대신 시간·비율·업무로. 모르면 "확인 중"으로 두고 2차 보고에서 보완.
🧾실무 팁 (SM 관점)
  • 장애 중에 메모장에 시각별로 기록(본 것·한 것)해 두면 보고서가 30분이면 끝나요
  • 보고서 초안은 당일, 재발 방지 완료 여부는 월간 운영보고서에서 추적
  • 재발 방지 항목은 체크리스트·점검표에 실제로 반영됐는지 다음 작업결과서로 확인
  • 같은 유형 장애가 반복되면 이전 보고서의 재발 방지가 실행됐는지부터 확인
✏️오늘의 퀴즈정답 확인 후 알았음/헷갈림 표시

Q1. "WAS 2호기가 옛 버전이었다"는 직접 원인일까, 근본 원인일까? 근본 원인은?

정답
직접 원인. 근본 원인은 배포 후 노드별 버전을 확인하는 절차가 없었던 것.

Q2. 좋은 재발 방지 대책이 갖춰야 할 네 가지는?

정답
무엇을(구체적 변경) · 누가 · 언제까지 · 완료 확인 방법.

Q3. MTTR은 무엇이고 무엇을 알려주나?

정답
인지 후 복구까지 걸린 시간. 복구 절차·도구가 충분했는지를 보여줘요(인지가 늦었는지는 MTTD).

Q4. 두 WAS 중 한 대만 문제인지 빠르게 확인하는 방법은?

정답
서버별 에러 건수 비교 grep -c "ERROR" was1/app.log was2/app.log, 배포 파일 md5sum 비교.
🚨장애 케이스 스터디 — 주문이 "가끔" 실패한다 — 두 대 중 한 대만가상의 일반 사례
증상09:02 오류율 알람. 사용자 문의: "주문 버튼을 누르면 될 때도 있고 안 될 때도 있어요." 같은 요청을 다시 누르면 성공하기도 한다.
  1. ① "가끔"이면 노드를 의심로드밸런서 뒤에 WAS가 여러 대면, 한 대만 이상해도 "가끔"으로 보여요.
    grep -c "ERROR" was1/app.log was2/app.log
# was1/app.log:0
# was2/app.log:1873
  2. ② 두 서버의 배포 파일 비교같은 버전이면 체크섬이 같아야 해요.
    md5sum /app/deploy/order-web.war
# 1호기: 3f2a...c91  /app/deploy/order-web.war
# 2호기: 8b7e...0d4  /app/deploy/order-web.war
  3. ③ 원인전날 배포를 1호기에만 반영. 확인은 대표 URL 1건으로만 해서 LB가 1호기로 보낸 응답만 보고 "정상" 판단.
  4. ④ 조치2호기를 LB에서 제외(09:31, 영향 즉시 차단) → 올바른 버전 재배포 → 헬스체크 확인 후 투입(09:48).
  5. ⑤ 재발 방지배포 체크리스트에 전 노드 md5 비교 추가, 노드별 헬스체크 URL로 버전 확인 자동화.

결함 관리 흐름
등록(Open) → 검토 → 할당(Assigned) → 수정(Fixed) → 확인 → 종료(Closed)
(수정 확인에 실패하면 재오픈)

심각도 vs 우선순위
구분뜻
심각도(Severity)결함이 시스템에 미치는 영향의 크기
우선순위(Priority)결함을 얼마나 빨리 고쳐야 하는지
출제 경향을 참고해 만든 연습 문제예요. 시험 일정·제도는 공식 사이트에서 확인하세요.
"심각도가 높으면 우선순위도 반드시 높다"는 단골 오답이에요. 둘은 별개로 정합니다.
✍️문제 1쉬움

결함이 시스템에 미치는 영향의 정도를 나타내는 것은?

정답 2번. 심각도는 영향의 크기, 우선순위는 수정의 시급성이에요.
✍️문제 2보통

일반적인 결함 상태 흐름으로 옳은 것은?

정답 1번. 등록(Open) → 담당 할당(Assigned) → 수정(Fixed) → 확인 후 종료(Closed). 확인 실패 시 다시 Open으로.
✍️문제 3함정

결함 관리에 대한 설명으로 틀린 것은?

정답 2번. 심각도가 높아도 사용 빈도가 낮으면 우선순위는 낮을 수 있고, 반대로 화면 오타처럼 심각도는 낮아도 우선순위가 높을 수 있어요.
