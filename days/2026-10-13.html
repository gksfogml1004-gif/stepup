인덱스는 "정렬된 목차" — 왜 어떤 조건은 빨라지고, 어떤 조건은 인덱스가 있어도 Full Scan이 되는지

  • 인덱스 = 키를 정렬해 두고 ROWID로 행을 찾아가는 목차
  • 컬럼 가공·앞 %·형변환은 정렬을 못 써서 Full Scan
  • 결합 인덱스는 선두 컬럼 조건이 있어야 제대로 탄다

PK와 UNIQUE 제약의 차이는?

정답
둘 다 중복을 막고 유니크 인덱스를 씁니다. PK는 NULL 불가·테이블당 1개, UNIQUE는 NULL을 허용하고 여러 개 둘 수 있어요.
💡개념 — B-Tree 인덱스는 이렇게 찾는다
1Root · Branch
"이 값은 어느 쪽?" 방향 안내몇 단계만 내려가면 리프에 도착
데이터가 많아도 깊이는 거의 그대로
2Leaf
정렬된 키 + ROWIDROWID = 행이 저장된 실제 위치 주소
3테이블 접근
ROWID로 테이블 행을 읽음필요한 컬럼이 인덱스에 다 있으면 생략 가능
4범위 스캔
리프끼리 연결돼 있어 옆으로 이어 읽기BETWEEN, >=, LIKE 'AB%'가 빠른 이유
📌 인덱스는 책 뒤의 찾아보기(정렬된 목차)예요. 정렬 순서를 그대로 쓸 수 있는 조건만 빠르게 찾을 수 있고, 정렬을 깨는 조건이면 목차가 있어도 처음부터 다 읽게(Full Scan) 됩니다.

인덱스가 있어도 못 타는 대표 패턴 3가지

컬럼 가공
TO_CHAR(order_dt,'YYYYMM')='202610'
→ 가공한 값은 목차에 없음
앞쪽 % LIKE
prod_nm LIKE '%노트북'
→ 시작 글자를 몰라 범위를 못 정함
묵시적 형변환
문자 컬럼 cust_id = 1001(숫자)
→ Oracle이 컬럼 쪽을 숫자로 바꿔 비교
🔬 심화 — 더 깊이 보기 (+5분)
① 결합 인덱스는 순서가 전부(CUST_ID, ORDER_DT) 인덱스는 전화번호부처럼 CUST_ID로 먼저, 같은 값 안에서 ORDER_DT로 정렬돼요. 그래서 CUST_ID 조건 없이 ORDER_DT만 주면 범위를 정할 수 없습니다(Index Skip Scan 같은 예외는 있음). 선두 컬럼은 항상 = 조건으로 쓰이는 컬럼이 유리해요.
② 인덱스보다 Full Scan이 나을 때인덱스는 ROWID로 테이블을 하나씩 찾아가는(랜덤 액세스) 비용이 들어요. 조건이 테이블의 큰 비율을 고르면 차라리 통째로 읽는 Full Scan이 빠르고, 옵티마이저도 그렇게 고릅니다. 이 판단은 통계 정보에 기대기 때문에 통계가 오래되면 엉뚱한 선택을 하기도 해요.
③ NULL과 인덱스 — DB마다 다르다Oracle의 B-Tree 인덱스는 인덱스 컬럼이 모두 NULL인 행은 저장하지 않아서 WHERE col IS NULL로는 단일 컬럼 인덱스를 못 씁니다. 결합 인덱스에 NOT NULL 컬럼을 함께 넣거나 기본값을 쓰는 식으로 풀어요. PostgreSQL은 NULL도 인덱스에 저장해 IS NULL 검색이 가능합니다.
④ 리뷰·면접에서 나오는 질문Q. 인덱스는 많을수록 좋은가요?
A. 조회는 빨라질 수 있지만 INSERT·UPDATE·DELETE 때마다 인덱스도 함께 갱신돼 쓰기가 느려지고 공간도 늘어요. 쿼리 패턴에 맞는 최소한의 인덱스를 두고, 안 쓰는 인덱스는 정리합니다.
🔎실습 1 · 테이블에 어떤 인덱스가 있나 (Oracle)
SELECT index_name, column_name, column_position
  FROM user_ind_columns
 WHERE table_name = 'TB_ORDER'
 ORDER BY index_name, column_position;
▶ 이렇게 나오면
INDEX_NAME    COLUMN_NAME  COLUMN_POSITION
------------  -----------  ---------------
IX_ORDER_01   CUST_ID                    1
IX_ORDER_01   ORDER_DT                   2
PK_TB_ORDER   ORDER_NO                   1
🔎 결과 읽는 법
  • COLUMN_POSITION이 결합 인덱스의 컬럼 순서예요
  • IX_ORDER_01은 CUST_ID가 선두 → ORDER_DT만 조건인 쿼리엔 효율이 낮아요
  • PK도 인덱스예요(PK_TB_ORDER). PK 조건 조회는 대부분 Unique Scan
  • 다른 스키마 테이블이면 all_ind_columns에 owner 조건을 추가

🔎 결과 읽는 법
  • 안쪽(들여쓰기 깊은 것)부터 읽어요: 인덱스 범위 스캔 → ROWID로 테이블 접근
  • TABLE ACCESS FULL이 보이면 테이블 전체를 읽는 것
  • BATCHED는 Oracle 12c 이상에서 보이는 표시예요
  • 자세한 해석(Cost, Rows)은 DB 트랙 2번째 주제 '실행계획 읽는 법'에서 다룹니다
🛠️실습 3 · 인덱스를 못 타는 조건 고치기
-- ✗ 컬럼 가공 → Full Scan
WHERE TO_CHAR(order_dt,'YYYYMM') = '202610'
-- ✓ 컬럼은 그대로, 값을 범위로
WHERE order_dt >= DATE '2026-10-01'
  AND order_dt <  DATE '2026-11-01'

-- ✗ 앞 % → 범위를 못 정함
WHERE prod_nm LIKE '%노트북'
-- ✓ 앞부분 고정이면 OK
WHERE prod_nm LIKE '노트북%'

-- ✗ 문자 컬럼에 숫자 → 형변환
WHERE cust_id = 1001
-- ✓ 타입 맞추기
WHERE cust_id = '1001'
💡 MyBatis에서도 같아요. 문자 컬럼에 숫자 타입 파라미터를 넘기면 형변환이 생길 수 있으니 VO 필드 타입을 컬럼 타입과 맞추세요. 날짜는 < 다음 달 1일 방식이 시·분·초까지 안전합니다.
⚠️흔한 실수현장에서 실제로 자주 나오는 것
  • "인덱스 만들었으니 끝"조건을 어떻게 쓰느냐에 따라 안 탈 수 있어요. 만든 뒤 실행계획으로 실제 사용 여부를 확인하세요.
  • 결합 인덱스 순서를 아무렇게나조회 화면의 필수 조건(항상 들어오는 = 조건)을 선두에 두지 않으면 인덱스가 반쪽짜리가 됩니다.
  • 운영 시간에 대형 테이블 CREATE INDEX생성 중 테이블 변경 작업(DML)이 대기할 수 있어요. 작업 시간대를 잡거나, DB 버전·에디션이 지원하면 ONLINE 옵션을 검토하세요.
  • 비슷한 인덱스 중복 생성(A), (A,B)처럼 겹치는 인덱스가 쌓이면 쓰기만 느려집니다. 추가 전에 기존 인덱스부터 조회하세요.
🧾실무 팁 (SM 관점)
  • 인덱스 추가도 변경관리 대상 — 영향도(쓰기 성능·공간·배치)와 롤백(DROP INDEX)을 이행계획에
  • 성능 개선 작업은 전후 실행계획·수행시간 캡처를 작업결과서에 남기기
  • SQL 리뷰 체크리스트에 "인덱스 컬럼 가공 금지, 타입 일치, 앞 % 금지" 3줄 넣기
  • 느린 화면 문의가 오면 먼저 해당 SQL의 실행계획부터 — 대부분 여기서 원인이 보여요

Q1. 인덱스가 (CUST_ID, ORDER_DT)일 때 WHERE order_dt = DATE '2026-10-13'만 쓰면?

정답
선두 컬럼(CUST_ID) 조건이 없어 일반적인 Range Scan을 못 해요. Full Scan이나 Skip Scan이 될 수 있습니다.

Q2. WHERE SUBSTR(order_no,1,4) = '2026'을 인덱스를 타게 고치면?

정답
WHERE order_no LIKE '2026%' — 컬럼은 그대로, 앞부분 고정 LIKE로.

Q3. 인덱스가 있는데도 옵티마이저가 Full Scan을 골랐다. 가능한 이유 두 가지는?

정답
조건이 테이블의 큰 비율을 고르는 경우, 또는 통계 정보가 오래돼 잘못 판단한 경우(그 외 컬럼 가공·형변환 등).

Q4. 인덱스를 많이 만들면 안 되는 이유는?

정답
INSERT·UPDATE·DELETE마다 인덱스도 갱신해야 해서 쓰기가 느려지고 저장 공간이 늘어나기 때문.

✍️문제 1쉬움

B-Tree 인덱스의 리프 블록에 저장되는 것으로 가장 적절한 것은?

정답 2번. 리프 블록에는 정렬된 인덱스 키와 ROWID가 있어서, 키로 찾은 뒤 ROWID로 테이블 행을 찾아갑니다.
✍️문제 2보통

PROD_NM 컬럼에 단일 인덱스가 있다. 인덱스 Range Scan이 가능한 조건은?

정답 1번. 앞부분이 고정된 LIKE는 정렬 순서로 범위를 정할 수 있어요. 앞쪽 %나 컬럼에 함수를 씌운 조건은 일반 인덱스로 범위를 정할 수 없습니다(함수 기반 인덱스가 따로 있으면 예외).
✍️문제 3함정

인덱스에 대한 설명으로 틀린 것은?

정답 3번. INSERT·UPDATE·DELETE 때는 인덱스도 함께 갱신해야 해서 인덱스가 많을수록 DML은 느려집니다.
🌐오늘의 기술 영어로그·문서·에러 메시지에서 자주 보는 표현
execution plan
실행계획
📍 DB 튜닝 문서·SQL 리뷰
Check the execution plan before and after adding the index.인덱스 추가 전후로 실행계획을 확인하세요.
full table scan
테이블 전체 스캔
📍 실행계획·성능 분석
The query performs a full table scan because the column is wrapped in a function.컬럼에 함수가 씌워져 있어 쿼리가 테이블 전체를 스캔한다.
index range scan
인덱스 범위 스캔
📍 실행계획
With the new index, the plan changed to an index range scan.새 인덱스로 실행계획이 인덱스 범위 스캔으로 바뀌었다.
implicit conversion
묵시적(자동) 형변환
📍 DB 문서·SQL 리뷰 코멘트
Avoid implicit conversion by matching the bind variable type.바인드 변수 타입을 맞춰 묵시적 형변환을 피하세요.
selectivity
선택도 (조건이 전체 중 몇 %의 행을 고르는지)

The index is useful only when the condition has good selectivity.조건이 적은 비율의 행만 고를 때(선택도가 좋을 때) 인덱스가 유용하다.
Oracle 실행계획은 영어 그대로 나와요. ACCESS / FILTER / FULL / RANGE / ROWID 다섯 단어만 알아도 절반은 읽힙니다.

Predicate Information (identified by operation id)
조건(WHERE절)이 실행계획의 몇 번 단계(Id)에서 쓰였는지 보여주는 영역
2 - access("CUST_ID"='C001')
access = 인덱스로 범위를 좁히는 데 쓰인 조건 → 좋음
1 - filter(TO_CHAR("ORDER_DT",...)='202610')
filter = 일단 읽은 뒤 걸러내기만 한 조건 → 인덱스에 못 쓰였다는 뜻
TO_CHAR("ORDER_DT",'YYYYMM')
컬럼이 가공돼 있어서 access가 아니라 filter로 밀려났어요
💡 느린 쿼리를 볼 때 "내가 기대한 조건이 access에 있나, filter에 있나"만 확인해도 원인이 빨리 보여요. Predicate 정보는 DBMS_XPLAN.DISPLAY를 기본(TYPICAL) 형식으로 출력하면 나옵니다.
인덱스 (Index)
키 값을 정렬해 두고 행의 위치를 가리키는 구조. 책의 찾아보기 역할
B-Tree
Root·Branch·Leaf로 이루어진 균형 트리. 대부분의 DB 기본 인덱스 구조
리프 블록 (Leaf Block)
B-Tree 맨 아래 단계. 정렬된 키와 ROWID가 저장되고 서로 연결돼 있음
ROWID
Oracle에서 행이 저장된 물리적 위치 주소. 인덱스가 테이블 행을 찾아갈 때 사용
Index Range Scan
인덱스 리프를 따라 조건 범위만 읽는 방식
Table Full Scan
테이블 전체를 처음부터 끝까지 읽는 방식 (실행계획: TABLE ACCESS FULL)
결합 인덱스 (Composite Index)
두 개 이상 컬럼으로 만든 인덱스. 컬럼 순서가 성능을 좌우함
선두 컬럼
결합 인덱스의 첫 번째 컬럼. 이 컬럼 조건이 있어야 범위를 좁힐 수 있음
묵시적 형변환
타입이 다른 값을 비교할 때 DB가 자동으로 타입을 바꾸는 것. 컬럼 쪽이 바뀌면 인덱스를 못 씀
옵티마이저 (Optimizer)
통계 정보를 바탕으로 SQL을 어떤 방법으로 실행할지(실행계획) 정하는 DB 엔진
execution plan
실행계획 — DB 튜닝 문서·SQL 리뷰
full table scan
테이블 전체 스캔 — 실행계획·성능 분석
index range scan
인덱스 범위 스캔 — 실행계획
implicit conversion
묵시적(자동) 형변환 — DB 문서·SQL 리뷰 코멘트
selectivity
선택도 (조건이 전체 중 몇 %의 행을 고르는지) — 옵티마이저·튜닝 문서
