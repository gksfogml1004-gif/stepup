실행계획 읽는 법

Operation·Rows·Cost·조인 방식을 읽고, "예상과 실제가 다른 곳"에서 느린 SQL의 원인을 찾는 법

  • 들여쓰기가 깊은 것부터, 같은 깊이면 위에서부터 읽기
  • E-Rows(예상)와 A-Rows(실제)가 크게 다르면 통계·조건부터 의심
  • Cost는 같은 SQL의 계획끼리만 비교 — 진짜 기준은 읽은 블록·시간

📌 실행계획은 옵티마이저의 "이렇게 할 생각"이에요. 느린 SQL의 원인은 대개 예상이 빗나간 곳(예상 1천 건, 실제 10만 건)에 있습니다.

자주 보는 Operation 3가지

TABLE ACCESS FULL
테이블 전체 읽기
→ 큰 테이블에서 소량 조회면 의심, 대량 조회면 정상일 수도
NESTED LOOPS
앞 결과 1건마다 뒤 테이블을 찾아감
→ 적은 건수 + 뒤 테이블 조인 컬럼 인덱스 필수
HASH JOIN
한쪽을 메모리 해시 테이블로 만들어 매칭
→ 대량 등가(=) 조인에 유리
🔬 심화 — 더 깊이 보기 (+5분)
① 예상이 아니라 실제를 보는 법EXPLAIN PLAN은 예상만 보여줘요. 실제로 몇 건을 읽었는지는 SQL을 실행한 뒤 DISPLAY_CURSOR로 봅니다. E-Rows vs A-Rows 차이가 큰 단계, Buffers(읽은 블록)가 큰 단계가 범인이에요.
SELECT /*+ gather_plan_statistics */ ...;

SELECT * FROM TABLE(
  DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL,
                            'ALLSTATS LAST'));
② Cost를 믿으면 안 되는 이유Cost는 옵티마이저가 통계로 계산한 상대 점수예요. 같은 SQL의 계획 A·B를 비교할 땐 쓸 수 있지만, 다른 SQL끼리 비교하거나 "Cost가 낮으니 빠르다"고 단정하면 안 됩니다. 통계가 틀리면 Cost도 같이 틀려요.
③ 바인드 변수와 실행계획 (MyBatis 연결)#{}는 바인드 변수라 SQL 모양이 같아 실행계획을 재사용해요. ${}로 값을 직접 박으면 값마다 다른 SQL이 되어 매번 새로 계획을 세우는(하드 파싱) 부담이 생깁니다. 첫날 복습 문제였던 인젝션 위험과 함께 ${}를 피할 이유가 하나 더 있는 셈이에요.
④ 리뷰·면접에서 나오는 질문Q. 느린 SQL의 실행계획에서 무엇부터 보나요?
A. ① 가장 많이 읽는 단계(FULL, Buffers 큰 곳) ② 예상 건수와 실제 건수 차이 ③ 조인 방식과 순서 ④ 조건이 access인지 filter인지 순으로 봅니다.
🧭실습 1 · 조인 실행계획 순서대로 읽기
EXPLAIN PLAN FOR
SELECT o.order_no, c.cust_nm
  FROM tb_order o
  JOIN tb_cust c ON c.cust_id = o.cust_id
 WHERE o.order_dt >= DATE '2026-10-01';

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
▶ 이렇게 나오면
-----------------------------------------------------------------
| Id | Operation                     | Name        | Rows | Cost |
-----------------------------------------------------------------
|  0 | SELECT STATEMENT              |             | 1200 |   58 |
|* 1 |  HASH JOIN                    |             | 1200 |   58 |
|  2 |   TABLE ACCESS BY INDEX ROWID | TB_ORDER    | 1200 |   41 |
|* 3 |    INDEX RANGE SCAN           | IX_ORDER_02 | 1200 |    5 |
|  4 |   TABLE ACCESS FULL           | TB_CUST     | 50000|   16 |
-----------------------------------------------------------------
🔎 결과 읽는 법
  • 읽는 순서: 3 → 2 → 4 → 1 → 0 (주문을 인덱스로 찾고, 고객 전체와 해시 조인)
  • *가 붙은 1·3번은 아래 Predicate 정보에 조건이 있다는 표시
  • 고객 5만 건 FULL은 해시 조인이면 흔한 모습 — 조회 건수가 아주 적다면 NESTED LOOPS + 인덱스가 나을 수도
  • 실제 화면엔 Bytes·Time 열도 나와요(여기선 생략)
🎯실습 2 · 예상 vs 실제 비교 (실행 후)
SELECT * FROM TABLE(
  DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL,
                            'ALLSTATS LAST'));
▶ 이렇게 나오면
| Id | Operation                    | Name        | E-Rows | A-Rows | Buffers |
|  2 |  TABLE ACCESS BY INDEX ROWID | TB_ORDER    |   1200 |  98000 |   45210 |
|* 3 |   INDEX RANGE SCAN           | IX_ORDER_02 |   1200 |  98000 |     310 |
🔎 결과 읽는 법
  • 예상 1,200건인데 실제 98,000건 → 옵티마이저 판단이 크게 틀림
  • Buffers 45,210: 테이블을 ROWID로 하나씩 찾아가느라 블록을 많이 읽음 → 이 단계가 범인
  • 원인 후보: 통계가 오래됨, 데이터 분포 쏠림 → 통계 갱신을 DBA와 검토
  • 바로 앞 SQL을 같은 세션에서 gather_plan_statistics 힌트로 실행해야 A-Rows가 나와요
🐢실습 3 · 느린 SQL 찾기 (DBA 권한 필요)
SELECT sql_id, executions,
       ROUND(elapsed_time / 1e6
             / GREATEST(executions, 1), 2) AS avg_sec,
       SUBSTR(sql_text, 1, 50) AS sql_text
  FROM v$sql
 ORDER BY elapsed_time DESC
 FETCH FIRST 5 ROWS ONLY;
▶ 이렇게 나오면
SQL_ID         EXECUTIONS  AVG_SEC  SQL_TEXT
-------------  ----------  -------  ------------------------
7h3kq2m9x1abc        1520     2.84  SELECT o.order_no, c.cus
4fz8w0p2n5def          12    41.10  SELECT * FROM tb_order W
🔎 결과 읽는 법
  • 총 소요 시간 순 상위 5개 — 자주 실행되며 느린 SQL이 먼저 보여요
  • AVG_SEC가 크면 한 번이 느린 것, EXECUTIONS가 크면 조금만 줄여도 효과 큼
  • 찾은 SQL_ID로 DBMS_XPLAN.DISPLAY_CURSOR('<sql_id>') 실행계획 확인
  • FETCH FIRST는 Oracle 12c 이상 문법 (이전 버전은 ROWNUM 사용)
⚠️흔한 실수현장에서 실제로 자주 나오는 것
  • Cost 숫자만 보고 판단통계가 틀리면 Cost도 틀려요. 실제 읽은 블록·시간(ALLSTATS)으로 확인하세요.
  • 개발 DB 실행계획을 운영과 같다고 가정데이터 양·분포·통계가 달라 계획이 바뀝니다. 중요한 SQL은 운영과 비슷한 데이터로 확인.
  • 힌트로 일단 빠르게 만들기데이터가 바뀌면 오히려 느려질 수 있고 원인(통계·인덱스)은 그대로예요. 힌트는 DBA와 합의한 최후 수단.
  • ${}로 값 직접 넣기값마다 다른 SQL이 되어 하드 파싱이 늘고 인젝션 위험까지. 값은 #{}로.
🧾실무 팁 (SM 관점)
  • 성능 개선 작업결과서에 전후 실행계획(ALLSTATS)과 수행 시간을 나란히 첨부
  • 느린 화면 문의 → SQL_ID 확보 → 실행계획 → 원인 순서를 장애 대응 매뉴얼에 정리
  • 통계 수집 주기·최근 수집 일자를 정기점검 항목에 넣기 (DBA 협의)
  • 튜닝 결과는 "빨라짐"이 아니라 "41초 → 0.8초, Buffers 45,210 → 820"처럼 숫자로

✍️문제 1쉬움

대용량 테이블끼리 등가(=) 조인할 때 해시 테이블을 만들어 처리하는 방식은?

정답 3번. HASH JOIN은 한쪽(보통 작은 쪽)으로 해시 테이블을 만들고 다른 쪽을 읽으며 매칭해요. 대량 등가 조인에 유리합니다.
✍️문제 2보통

NESTED LOOPS 조인에 대한 설명으로 옳은 것은?

정답 2번. NESTED LOOPS는 선행 결과 한 건마다 후행 테이블을 찾아가요. 그래서 후행 테이블 조인 컬럼 인덱스가 성능을 좌우합니다.

정답 2번. HASH JOIN은 해시값이 같은지로 매칭하므로 등가 조인에서만 쓸 수 있어요.

💡 before ~ing(~하기 전에), focus on(~에 집중하라) — 튜닝 가이드의 순서·우선순위는 이런 표현으로 나와요.
실행계획 (Execution Plan)
옵티마이저가 정한 SQL 처리 순서와 방법
Cost
옵티마이저가 통계로 계산한 상대 비용 점수. 실제 시간과 다를 수 있음
E-Rows / A-Rows
실행계획의 예상 건수 / 실제 건수. 차이가 크면 통계 문제 의심
Buffers
SQL 실행 중 읽은 블록 수. 성능 판단의 실질 지표
NESTED LOOPS 조인
앞 결과 한 건마다 뒤 테이블을 찾아가는 조인. 소량·인덱스 있을 때 유리
HASH JOIN
한쪽을 해시 테이블로 만들어 매칭하는 조인. 대량 등가 조인에 유리
통계 정보
테이블·인덱스의 건수·분포 정보. 옵티마이저가 실행계획을 정하는 근거
바인드 변수
SQL에 값 대신 자리표시(?)를 두고 실행 때 값을 넣는 방식. MyBatis #{}
하드 파싱
SQL을 처음 보고 실행계획을 새로 만드는 작업. 많으면 DB 부하
SQL_ID
Oracle이 SQL 문장마다 붙이는 식별자. 실행계획·통계 조회에 사용
cardinality
(예상) 건수 — 옵티마이저·튜닝 문서
stale statistics
오래된 통계 — DB 튜닝 문서·DBA 코멘트
nested loops / hash join
중첩 루프 조인 / 해시 조인 — 실행계획
bind variable
바인드 변수 — DB·JDBC 문서
hint
힌트 (실행계획 지시 주석) — SQL·튜닝 리뷰
