💡개념 — 로그를 다루는 네 가지 동작
1지켜보기
tail -F새로 쌓이는 줄을 실시간으로
-F는 롤링돼도 새 파일을 따라감
2찾기
grep-n 줄번호 · -i 대소문자 무시
-B/-A 앞뒤 문맥 · -v 제외
3넓게 보기
less파일 전체를 안 읽고 필요한 만큼만
/검색 · n 다음 · G 끝 · F 실시간
4세기
awk · sort · uniq -c시간대별·코드별 건수 집계
파이프(|)로 이어 붙이기
📌 리눅스 명령은 파이프(|)로 이어 붙이는 레고예요. "찾고 → 자르고 → 정렬하고 → 센다"를 한 줄로 만들 수 있으면 로그 분석의 80%는 끝납니다.

자주 헷갈리는 3가지

tail -f vs tail -F
-f는 로그가 롤링되면 옛 파일을 계속 봄 → "로그가 안 찍혀요" 착각
-F는 새 파일을 다시 열어 따라감
vi로 큰 로그 열기
수 GB 파일을 통째로 메모리에 올려 서버가 느려질 수 있음
→ less는 필요한 부분만
grep -c vs uniq -c
grep -c: 전체 건수 하나
sort | uniq -c: 종류별 건수
🔬 심화 — 더 깊이 보기 (+5분)
① 시간 범위만 잘라 보기로그가 "날짜 시간 레벨 메시지" 형식이면 awk로 시간 열을 비교할 수 있어요. 시간 문자열이 같은 형식(HH:MM:SS)이면 문자열 비교로도 범위가 맞습니다.
# 09:00:00 ~ 09:10:00 사이 줄만
awk '$2 >= "09:00:00" && $2 <= "09:10:00"' app.log
# 그중 ERROR만
awk '$2 >= "09:00:00" && $2 <= "09:10:00" \
     && /ERROR/' app.log
② 롤링·압축된 지난 로그지난 날짜 로그는 app.log.2026-10-20.gz처럼 압축돼 있는 경우가 많아요. 풀지 않고 zgrep, zcat | grep으로 바로 검색합니다. 풀어서 복사하면 디스크가 찰 수 있어요(10/14 복습).
③ 서버 시간대부터 확인서버·로그가 UTC로 찍히면 한국 시간(KST)보다 9시간 느려요. 사용자가 "9시에 오류"라고 하면 UTC 로그에선 00시를 봐야 합니다. date나 timedatectl로 먼저 확인하고, 장애보고서엔 KST로 통일해 적으세요.
④ 리뷰·면접에서 나오는 질문Q. 운영 로그에서 특정 에러가 언제부터 몇 번 났는지 어떻게 보나요?
A. grep으로 에러 줄을 뽑고, 시간 앞부분만 cut으로 잘라 sort | uniq -c로 시간대별 건수를 셉니다. 처음 나온 시각은 grep -m 1로 확인해요.
👀실습 1 · 실시간으로 에러만 지켜보기
tail -F /app/logs/app.log \
  | grep --line-buffered -E "ERROR|Exception"
▶ 이렇게 나오면
2026-10-21 09:12:03 ERROR [exec-7] OrderService - 주문 저장 실패
java.sql.SQLException: ORA-00001: unique constraint violated
🔎 결과 읽는 법
  • -E로 여러 단어를 |(또는)로 묶어 찾기
  • --line-buffered를 빼면 파이프 뒤 출력이 몇 초씩 늦게 보일 수 있어요
  • 끝낼 땐 Ctrl+C — 운영 서버에 켜 둔 채 자리 비우지 않기
🔎실습 2 · 앞뒤 문맥과 건수
# 첫 발생 위치 (줄번호 포함, 1건만)
grep -n -m 1 "OutOfMemoryError" app.log
# 앞 3줄, 뒤 10줄까지 함께 보기
grep -n -B 3 -A 10 "OutOfMemoryError" app.log | less
# 전체 에러 건수
grep -c "ERROR" app.log
▶ 이렇게 나오면
18452:2026-10-21 09:12:03 ERROR [exec-7] Request processing failed
...
1287
🔎 결과 읽는 법
  • -m 1: 처음 한 건만 → 언제부터 시작됐는지
  • -B/-A로 에러 직전 상황(어떤 요청이었나)과 Caused by까지 한 번에
  • 결과가 길면 | less로 넘겨 위아래로 이동하며 보기
📊실습 3 · 시간대별 에러 집계
# 로그 형식: 2026-10-21 09:12:03 ERROR ...
grep "ERROR" app.log \
  | cut -c1-13 | sort | uniq -c
▶ 이렇게 나오면
      3 2026-10-21 08
    152 2026-10-21 09
     11 2026-10-21 10
🔎 결과 읽는 법
  • cut -c1-13: 앞 13글자(날짜 + 시) → 시간 단위로 묶기
  • 09시에 152건 급증 → 그 시각 전후에 무엇이 바뀌었나(배포·배치·트래픽) 확인
  • 분 단위로 보려면 cut -c1-16
🌐실습 4 · 액세스 로그로 응답 코드 세기
# 형식 예: 192.0.2.50 - - [21/Oct/2026:09:12:03 +0900]
#          "GET /api/orders HTTP/1.1" 502 312
awk '{print $9}' access.log | sort | uniq -c | sort -rn
▶ 이렇게 나오면
  48210 200
   1532 502
    204 404
     12 500
🔎 결과 읽는 법
  • $9는 공백으로 나눈 9번째 칸 = HTTP 상태 코드 (로그 형식에 따라 위치가 다를 수 있음)
  • sort -rn: 건수 많은 순
  • 502가 1,532건 → 10/15에 배운 대로 뒤쪽 WAS 상태부터
⚠️흔한 실수현장에서 실제로 자주 나오는 것
  • 수 GB 로그를 vi로 열기메모리를 크게 써서 운영 서버가 느려질 수 있어요. less나 grep으로.
  • tail -f로 보다 "로그가 안 찍힌다" 판단자정 롤링 후엔 옛 파일을 보고 있을 수 있어요. -F를 쓰거나 파일을 다시 열기.
  • 에러 한 줄만 보고 원인 판단진짜 원인은 아래 Caused by에 있어요. -A로 뒤까지 보세요.
  • 서버 시간대를 확인하지 않음UTC 로그를 KST로 착각하면 엉뚱한 시간대를 봅니다. date로 먼저 확인.
🧾실무 팁 (SM 관점)
  • 장애 문의가 오면 첫 발생 시각(grep -m 1)과 시간대별 건수를 먼저 뽑아 공지·보고서에 사용
  • 장애보고서 타임라인은 로그 시각을 근거로, 시간대는 KST로 통일
  • 로그 형식(날짜 위치·레벨)을 운영 매뉴얼에 적어 두면 누구나 같은 명령을 쓸 수 있어요
  • 자주 쓰는 조합은 치트시트에 쌓아 두고 복사해서 사용

tail -F
파일 끝을 실시간으로 보며, 파일이 교체(롤링)돼도 새 파일을 따라가는 옵션
grep 문맥 옵션 (-B/-A/-C)
찾은 줄의 앞(Before)·뒤(After)·앞뒤(Context) N줄을 함께 출력
파이프 (|)
앞 명령의 출력을 뒤 명령의 입력으로 넘기는 기호
정규표현식 (Regex)
문자열 패턴을 표현하는 규칙. grep -E "ERROR|WARN"처럼 사용
awk
줄을 칸(필드)으로 나눠 조건·출력을 처리하는 텍스트 처리 도구. $1, $2…
uniq -c
연속된 같은 줄을 하나로 묶고 개수를 세는 명령. 보통 sort 뒤에 사용
액세스 로그 (Access Log)
웹서버가 요청마다 남기는 기록(IP·시각·URL·상태 코드·크기)
로그 레벨 (Log Level)
로그 중요도 등급. DEBUG < INFO < WARN < ERROR
UTC / KST
협정 세계시 / 한국 표준시(UTC+9). 서버 로그 시간 해석의 기준
tail the log
로그를 실시간으로 지켜보다 — 운영 매뉴얼·메신저
grep for
~을 grep으로 찾다 — 운영 대화·이슈 코멘트
log rotation
로그 롤링(교체·보관) — 서버 설정 문서
timestamp
(로그에 찍힌) 시각 — 로그·장애 보고
UTC offset
UTC와의 시차 — 로그 형식·서버 설정
