  • 요구사항은 수용 기준(조건·기준값)까지 적어야 테스트가 된다
  • 영향도 = 호출처 검색 → 화면·DB·배치·연계·권한 판단 → 근거 기록

개발 전, 변경이 다른 화면·배치·연계에 미치는 범위를 정리하는 문서는?

정답
영향도 분석서 — 오늘 이걸 제대로 쓰는 법을 봅니다.
💡개념 — 요구 접수부터 추적까지 4단계
1접수
요청 원문 그대로 기록누가·언제·어떤 화면에서
해석은 다음 단계에서
2정의
요구ID · 기능/비기능 · 수용 기준"빠르게" → "3초 이내(조건 포함)"
모르는 건 가정으로 적고 확인
3영향도
화면·DB·배치·연계·권한소스·DB 의존성 검색 결과를
근거로 첨부
4추적
요구ID ↔ 프로그램 ↔ 테스트커밋·테스트 케이스에 요구ID
→ 빠진 것 없이 확인
📌 좋은 요구사항의 기준은 하나예요. "이 문장으로 테스트 케이스를 만들 수 있는가?" 만들 수 없으면 아직 덜 정의된 거예요.

같은 요청, 이렇게 다르게 적힌다

테스트할 수 없음
"주문 조회 속도를 개선한다."
→ 얼마나? 어떤 조건에서? 끝났는지 알 수 없음
테스트할 수 있음
"주문 조회(기간 1개월, 결과 1만 건 이하)는 3초 이내 응답한다." (숫자는 예시)
기능 vs 비기능
기능: 무엇을 한다 (기간 검색 추가)
비기능: 얼마나 잘 (성능·보안·가용성)
🔬 심화 — 더 깊이 보기 (+5분)
① 요구사항 추적표(RTM)요구ID마다 설계 → 프로그램 → 테스트 케이스 → 결과를 한 줄로 잇는 표예요. 누락(구현 안 된 요구, 요구 없는 개발)을 찾는 도구이고, 점검·감리 때 가장 먼저 보는 문서 중 하나입니다. 10/09에 배운 추적성을 문서로 만든 것이에요.
② 영향도 분석을 깊게 하는 법정적 분석(소스·DB 객체 검색)으로 후보를 뽑고, 필요하면 동적 확인(접근 로그·실제 호출 이력)으로 정말 쓰이는지 봐요. DB는 테이블을 참조하는 뷰·프로시저까지 확인하고, 공통 모듈 변경은 호출하는 모든 화면이 영향 범위라 가장 신중해야 합니다.
-- 테이블을 참조하는 DB 객체 (Oracle)
SELECT owner, name, type
  FROM all_dependencies
 WHERE referenced_name = 'TB_ORDER';
③ 요구사항 변경 관리개발 중에 요구가 바뀌면 변경 요청으로 다시 받아 영향·일정을 재산정하고 합의해요. 합의된 범위(베이스라인)가 있어야 "원래 그 기능도 포함 아니었어요?" 같은 범위 다툼을 막을 수 있습니다. 메신저로 바뀐 내용도 정의서 버전 이력에 남기세요.
④ 리뷰·면접에서 나오는 질문Q. 영향도 분석은 어떻게 하셨나요?
A. 변경 대상의 호출처를 소스·DB 의존성으로 검색하고, 화면·배치·연계·권한·데이터 관점으로 판단해 근거(검색 결과)와 함께 기록했습니다. 그 결과로 회귀 테스트 범위를 정했습니다.
📝실습 1 · 요구사항 한 건 정의하기 (일반 양식)
요구ID    : REQ-ORD-012
요구명    : 주문 조회 기간 검색 추가
구분      : 기능
내용      : 주문 조회 화면에서 주문일자
            시작~종료로 검색할 수 있다
수용 기준 : ① 최대 기간 3개월
            ② 3초 이내 응답 (예시)
            ③ 종료일 < 시작일이면 안내 메시지
요청      : 현업 담당 / 2026-10-16
우선순위  : 상
가정·미결 : 엑셀 다운로드도 같은 조건 적용?
            → 10/17까지 확인 요청
🔎 결과 읽는 법
  • 수용 기준 ①②③이 그대로 테스트 케이스가 돼요
  • 가정·미결 칸이 핵심 — 내가 추측한 걸 숨기지 말고 적어서 확인받기
  • 요구ID를 커밋 메시지·테스트 케이스에도 똑같이 → 추적 가능
🔍실습 2 · 소스에서 영향 범위 찾기
# 테이블을 쓰는 파일 목록만
grep -rln "TB_ORDER" src/ | sort
▶ 이렇게 나오면
src/main/java/com/example/batch/OrderSettleJob.java
src/main/resources/mapper/OrderMapper.xml
src/main/resources/mapper/StatMapper.xml
🔎 결과 읽는 법
  • 화면(OrderMapper) 외에 정산 배치와 통계도 같은 테이블을 씀 → 테스트 범위에 포함
  • -l은 파일명만 보여줘서 영향도 분석서에 붙이기 좋아요
  • 검색어는 테이블명·컬럼명·프로그램ID를 각각 돌려 보세요
🗄️실습 3 · DB 쪽 영향 범위 찾기 (Oracle)
SELECT owner, name, type
  FROM all_dependencies
 WHERE referenced_name = 'TB_ORDER';

-- 반영 후 깨진 객체 확인
SELECT object_name, object_type
  FROM user_objects
 WHERE status = 'INVALID';
▶ 이렇게 나오면
OWNER   NAME              TYPE
------  ----------------  ------------
APPUSR  VW_ORDER_SUMMARY  VIEW
APPUSR  PKG_SETTLE        PACKAGE BODY
🔎 결과 읽는 법
  • 뷰·패키지가 테이블을 참조 → 컬럼 변경 시 INVALID가 될 수 있어요
  • 반영 직후 INVALID 객체를 조회해 재컴파일까지가 작업 범위
  • 소스 검색(실습 2)과 DB 검색(실습 3)을 둘 다 해야 빠짐이 없어요
💡 패키지 재컴파일: ALTER PACKAGE PKG_SETTLE COMPILE BODY; — 운영 반영 절차에 넣어 두세요.
✅영향도 분석 체크리스트
  • 화면: 같은 테이블·공통 모듈을 쓰는 다른 화면
  • 배치·통계: 야간 배치, 집계·통계 쿼리 (가장 자주 빠짐)
  • DB 객체: 뷰·프로시저·트리거·임시 테이블
  • 연계: 외부 기관·타 시스템 인터페이스 항목·길이
  • 권한·보안: 메뉴 권한, 개인정보 항목 노출
  • 데이터·운영: 기존 데이터 보정, 서비스 중단 여부
⚠️ 각 항목에 "영향 있음/없음 + 근거"를 남겨야 나중에 설명할 수 있어요.
⚠️흔한 실수현장에서 실제로 자주 나오는 것
  • 요청 원문만 옮겨 적고 수용 기준 없음"개선한다"로 끝나면 언제 끝났는지 아무도 판단 못 해요. 기준값과 조건을 꼭 물어서 적으세요.
  • 메신저로 바뀐 요구를 그냥 반영나중에 "그런 말 한 적 없다"가 됩니다. 정의서 버전을 올리고 변경 이력을 남기세요.
  • 영향도 분석을 화면만 봄배치·통계·연계가 가장 자주 빠지고, 장애는 대개 다음 날 아침에 터져요(아래 케이스 스터디).
  • 공통 모듈 수정을 가볍게 봄공통 코드·유틸 한 줄이 수십 개 화면에 영향을 줍니다. 호출처 전체를 뽑아 회귀 테스트 범위를 넓게 잡으세요.
🧾실무 팁 (SM 관점)
  • 요구사항정의서에 가정·미결 칸을 두고, 확인 요청 기한까지 적기
  • 요구ID를 커밋 메시지·테스트 케이스·작업결과서에 똑같이 → 추적표가 저절로 채워져요
  • 영향도 분석서에 grep·DB 의존성 검색 결과를 그대로 첨부
  • 변경이 생기면 정의서 버전(v1.0 → v1.1)과 변경 사유·요청자·일자 기록
✏️오늘의 퀴즈정답 확인 후 알았음/헷갈림 표시

Q1. "화면 속도를 개선해 주세요"를 테스트 가능한 요구사항으로 바꾸려면 무엇을 물어야 할까?

정답
어떤 화면·동작(첫 로딩/검색), 조건(기간·건수), 목표 기준값(예: 3초 이내).

Q2. 주문번호 컬럼 길이를 늘린다. 영향도 분석에서 확인할 곳을 4가지 이상 들면?

정답
같은 컬럼을 쓰는 화면, 배치·통계, 참조 뷰·프로시저·임시 테이블, 연계 인터페이스의 항목 길이, 엑셀·보고서 양식.

Q3. 기능 요구사항과 비기능 요구사항의 예를 하나씩 들면?

정답
기능: 기간 검색 추가 / 비기능: 3초 이내 응답, 접근 권한 통제, 99.9% 가용성 등.

Q4. 개발 중에 현업이 메신저로 "이것도 추가해 주세요"라고 했다. 어떻게 처리할까?

정답
변경 요청으로 받아 영향·일정을 재산정해 합의하고, 정의서 버전·변경 이력에 남깁니다.
🚨장애 케이스 스터디 — 배포 다음 날 아침, 정산 배치가 실패했다가상의 일반 사례
증상주문번호 길이 확장 배포 다음 날 08:50, 정산 담당자가 "어제 정산 결과가 안 보여요"라고 연락. 화면 자체는 정상.
  1. ① 확인 — 배치 로그부터화면이 정상이면 야간 작업을 의심합니다.
    grep -n "ORA-" /app/batch/logs/settle_20261016.log | tail -3
# ORA-12899: value too large for column
#   "APPUSR"."TMP_SETTLE"."ORDER_NO" (actual: 20, maximum: 15)
  2. ② 원인주문번호를 15 → 20자리로 늘렸는데, 정산 배치가 쓰는 임시 테이블(TMP_SETTLE)은 그대로 15자리. 영향도 분석 때 화면 소스만 검색하고 배치·DB 객체를 안 봤어요.
  3. ③ 조치임시 테이블 컬럼 확장 → 배치 재수행 → 정산 건수·금액 정합성 확인 → 담당자에게 복구 공지.
  4. ④ 재발 방지영향도 체크리스트에 배치·통계·DB 객체를 필수 항목으로 추가, 분석서에 grep·all_dependencies 결과 첨부 의무화.

재발방지: 영향도 분석 체크리스트에 배치·DB 객체 필수화, 검색 근거 첨부
💡 이 장애는 기술보다 영향도 분석 절차의 구멍이에요. 장애보고서의 재발 방지가 "주의하겠다"가 아니라 체크리스트·절차 변경이어야 하는 이유입니다.

"응답 시간·보안·가용성"이 보이면 비기능이에요. 기능 목록 속에 하나 섞어 내는 문제가 단골.
✍️문제 1쉬움

다음 중 비기능 요구사항은?

정답 3번. 응답 시간(성능)은 비기능 요구사항이에요. 나머지는 시스템이 "무엇을 하는가"를 말하는 기능 요구사항.
✍️문제 2보통

요구사항 개발 프로세스의 순서로 옳은 것은?

정답 1번. 요구를 모으고(도출) → 정리·충돌 해결(분석) → 문서화(명세) → 맞게 적었는지 검증(확인) 순서입니다.
✍️문제 3함정

요구사항 명세 기법에 대한 설명으로 틀린 것은?

정답 3번. 수학적 기호를 쓰는 건 정형 명세예요. 비정형 명세는 자연어 기반이라 이해는 쉽지만 모호해질 수 있어요.
