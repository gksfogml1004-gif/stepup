equals/hashCode, String 불변성

"같다"에는 두 가지 뜻이 있다 — 문자열 비교 버그와 HashMap에서 객체를 못 찾는 버그의 공통 원인

  • ==는 같은 객체(주소), equals()는 같은 내용

  • String은 불변: 비교는 "Y".equals(x), 반복 연결은 StringBuilder

📌 HashMap·HashSet은 hashCode로 칸을 찾고 → equals로 확인해요. 그래서 equals만 고치고 hashCode를 안 고치면, 내용이 같은 객체도 다른 칸을 뒤져서 못 찾습니다.

🔬 심화 — 더 깊이 보기 (+5분)
① equals·hashCode 규약equals가 true면 hashCode는 반드시 같아야 해요. 반대로 hashCode가 같다고 equals가 true일 필요는 없어요(해시 충돌). equals는 반사성(x.equals(x))·대칭성·추이성·일관성, 그리고 x.equals(null)은 false여야 합니다.
② HashMap 키 객체를 바꾸면 사라진다키로 넣은 객체의 필드를 나중에 바꾸면 hashCode가 달라져 원래 칸에서 못 찾아요(메모리에는 남아 누수처럼 보이기도). 그래서 키는 String·Long 같은 불변 객체나 필드를 바꾸지 않는 객체를 씁니다.
③ String이 불변인 이유와 연결 성능불변이라 상수 풀로 공유할 수 있고, 여러 스레드가 써도 안전하며, 해시값도 캐시할 수 있어요. 한 줄 안의 + 연결은 컴파일러가 최적화하지만, 반복문 안의 +=는 매번 새 객체를 만들어 대량일 때 느려집니다 → StringBuilder. Lombok @Data를 JPA 엔티티에 쓰면 연관 필드까지 equals에 들어가 문제가 생길 수 있으니 주의.
④ 리뷰·면접에서 나오는 질문Q. equals만 재정의하고 hashCode를 안 하면 어떤 문제가 생기나요?
A. 내용이 같은 두 객체가 다른 hashCode를 가져서 HashMap·HashSet이 다른 칸을 찾아요. 그래서 get이 null을 주거나 Set에 중복이 들어갑니다.

class OrderKey {

    return o instanceof OrderKey

  }
  // hashCode 재정의 없음
}
Set<OrderKey> set = new HashSet<>();
set.add(new OrderKey("A1"));

⚠️흔한 실수현장에서 실제로 자주 나오는 것
  • 문자열을 ==로 비교테스트(리터럴)에선 통과하고 운영(입력값)에서 가끔 틀려요. 찾기 어려운 버그 1순위.
  • equals만 재정의HashSet 중복·HashMap get null. 둘은 항상 같이 재정의하세요.
  • HashMap 키로 쓴 객체의 값을 변경넣은 뒤 키 필드를 바꾸면 그 항목을 다시 못 찾아요. 키는 불변으로.
  • 변수.equals("상수")로 NPEnull이 들어오면 바로 터져요. "상수".equals(변수) 또는 Objects.equals.

Q1. a == c는 false인데 a.equals(c)는 true. 왜일까?

정답
==는 주소(같은 객체인지), equals는 내용을 비교. 내용은 같지만 서로 다른 객체예요.

Q2. equals만 재정의한 키로 HashMap.get을 했더니 null. 이유는?

정답
hashCode를 재정의하지 않아 내용이 같아도 다른 칸을 찾기 때문. hashCode도 함께 재정의해야 해요.

Q3. "Y".equals(status)가 status.equals("Y")보다 안전한 이유는?

정답
status가 null이어도 NPE가 나지 않고 false를 돌려주기 때문.

Q4. 반복문에서 수만 번 str += x를 하면 왜 느릴까?

정답
String은 불변이라 매번 새 객체를 만들고 복사해요. StringBuilder는 한 버퍼에 이어 붙입니다.

✍️문제 3함정

equals와 hashCode에 대한 설명으로 틀린 것은?

정답 2번. hashCode가 같아도 내용이 다를 수 있어요(해시 충돌). 그래서 같은 칸 안에서 equals로 한 번 더 비교합니다.
🌐오늘의 기술 영어로그·문서·에러 메시지에서 자주 보는 표현
override
(메서드를) 재정의하다
📍 코드·리뷰 코멘트
You should override hashCode() whenever you override equals().equals()를 재정의할 때마다 hashCode()도 재정의해야 한다.
immutable
불변의 (바꿀 수 없는)
📍 Java 문서·설계 리뷰
String objects are immutable, so concatenation creates a new object.String은 불변이라 연결하면 새 객체가 생긴다.
equality vs. identity
동등성(내용) vs 동일성(같은 객체)
📍 Java 문서·기술 블로그
Use equals() for equality and == for identity.내용 비교는 equals(), 같은 객체 확인은 ==.
hash collision
해시 충돌
📍 자료구조 문서
Different keys may have the same hash code, which is called a hash collision.서로 다른 키가 같은 해시코드를 가질 수 있는데 이를 해시 충돌이라 한다.
null-safe
null이 와도 안전한
📍 코드 리뷰·유틸 문서
Objects.equals() is a null-safe way to compare two objects.Objects.equals()는 null에 안전한 비교 방법이다.
