💡개념 — TCP/IP 4계층으로 보는 장애 위치
1네트워크 접근 (L1·L2)
케이블·랜카드·MAC 주소ip -br link로 UP/DOWN
담당: 망·인프라
2인터넷 (L3)
IP 주소·라우팅ping, traceroute, ip route
담당: 망
3전송 (L4)
TCP/UDP·포트nc -zv, ss
담당: 보안(방화벽)·서버
4응용 (L5~L7)
HTTP·DNS·TLScurl -v, nslookup
담당: 개발·WAS
📌 10/08에 배운 "ping → 포트 → 응답" 3단계가 바로 L3 → L4 → L7 확인이었어요. 아래층이 통과해야 위층을 의심할 의미가 있습니다.

증상으로 계층 가르기

경로가 끊김 (L3)
traceroute가 중간에서 멈춤, 게이트웨이 무응답
→ 망 담당에게 구간 전달
포트만 안 됨 (L4)
ping OK인데 포트 timeout / refused
→ 방화벽 또는 서비스 기동
연결 OK, 응답 이상 (L7)
Connected to 후 404·502·504·인증서 오류
→ 웹서버·WAS·애플리케이션
🔬 심화 — 더 깊이 보기 (+5분)
① 캡슐화 — 장비마다 보는 깊이가 다르다보낼 데이터에 TCP 헤더(포트) → IP 헤더(IP) → 이더넷 헤더(MAC)가 차례로 붙어요. 그래서 스위치는 MAC(L2), 라우터는 IP(L3), L4 로드밸런서·방화벽은 IP+포트, L7 장비는 URL·쿠키까지 보고 판단합니다. "L4 장비라 URL별 분배가 안 된다" 같은 말이 여기서 나와요.
② TCP와 UDPTCP는 연결을 맺고 순서·재전송을 보장(HTTP, DB 연결). UDP는 연결 없이 빠르게 보냄(DNS 조회, NTP, syslog 기본). UDP는 응답을 기대하지 않아서 nc -u로 "열렸다"가 나와도 확실하지 않아요. 실제 서비스 요청(예: nslookup)으로 확인하는 게 정확합니다.
③ 502와 504 — 웹서버 뒤 WAS 구조에서Apache·WebtoB 같은 웹서버(또는 L7 장비)가 앞, WAS가 뒤에 있을 때:
502 Bad Gateway — 뒤에서 정상 응답을 못 받음(WAS 다운, 연결 거부)
504 Gateway Timeout — 뒤가 제한 시간 안에 응답 안 함(WAS 처리 지연, DB 느림)
→ 502면 WAS 기동·포트부터, 504면 WAS 스레드 덤프·느린 SQL부터.
④ 리뷰·면접에서 나오는 질문Q. OSI 7계층을 실무에서 어디에 쓰나요?
A. 장애 때 어느 층에서 끊겼는지로 범위를 좁히고, 망(L1~L3)·보안(L4)·개발(L7) 중 누가 볼지 정하는 기준으로 씁니다. 각 층마다 확인 명령과 증거를 남기면 책임 공방 없이 빨리 해결돼요.
🧭실습 1 · L3: 내 IP와 경로 확인
# 인터페이스 상태와 IP (간단히)
ip -br addr
# 라우팅: 다른 대역은 어디로 나가나
ip route
# 목적지까지 경로 (Windows: tracert -d)
traceroute -n 192.0.2.10
▶ 이렇게 나오면
lo      UNKNOWN  127.0.0.1/8
eth0    UP       192.0.2.11/24

default via 192.0.2.1 dev eth0
192.0.2.0/24 dev eth0 proto kernel scope link src 192.0.2.11
🔎 결과 읽는 법
  • UP이어야 랜카드가 살아 있는 것, IP는 /24 같은 대역 표기와 함께
  • default via가 게이트웨이 — 다른 대역으로 가는 문
  • 같은 대역(192.0.2.0/24)은 게이트웨이 없이 직접 통신
  • traceroute에서 * * *가 계속되면 그 구간을 망 담당에게 전달 (ICMP를 막은 장비일 수도 있음)
🔌실습 2 · L4: 연결 상태 한눈에 보기
# TCP 연결을 상태별로 세기
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c
# 닫히지 않고 쌓이는 연결과 프로세스
ss -tanp state close-wait | head
▶ 이렇게 나오면
    312 ESTAB
     18 LISTEN
    845 TIME-WAIT
     57 CLOSE-WAIT
🔎 결과 읽는 법
  • ESTAB: 연결 중. 평소보다 급증하면 요청 폭주나 커넥션 풀 문제
  • TIME-WAIT: 내가 먼저 끊은 연결의 정리 대기. 많아도 대개 정상
  • CLOSE-WAIT가 계속 늘면 우리 프로그램이 소켓을 안 닫는 것 → 연결 누수 버그 의심
  • -p로 어떤 프로세스의 연결인지 확인 (root 권한 필요할 수 있음)
🌐실습 3 · L7: HTTP 요청·응답 들여다보기
# 본문은 버리고 요청/응답 헤더만
curl -sv -o /dev/null http://192.0.2.10/api/health
▶ 이렇게 나오면
*   Trying 192.0.2.10:80...
* Connected to 192.0.2.10 (192.0.2.10) port 80
> GET /api/health HTTP/1.1
> Host: 192.0.2.10
> User-Agent: curl/7.76.1
>
< HTTP/1.1 502 Bad Gateway
< Content-Type: text/html
🔎 결과 읽는 법
  • Connected to가 보이면 L3·L4는 통과 — 네트워크 탓이 아님
  • >는 내가 보낸 요청, <는 받은 응답
  • 502 → 웹서버는 살아 있고 뒤의 WAS가 문제. WAS 기동·포트부터
  • HTTPS면 SSL certificate problem 같은 줄로 인증서 문제도 여기서 보여요
⚠️흔한 실수현장에서 실제로 자주 나오는 것
  • 모든 연결 문제를 "네트워크 문제"로 넘김망 담당은 증거 없이는 움직이기 어려워요. 어느 층까지 통과했는지 결과와 함께 요청하세요.
  • 502와 504를 같은 장애로 처리502는 WAS가 응답 불가(다운·거부), 504는 응답이 느림. 확인할 곳이 완전히 달라요.
  • CLOSE-WAIT 증가를 방치소켓을 안 닫는 버그는 시간이 지나면 연결·파일 핸들 고갈로 장애가 돼요. 추이를 보고 코드의 close 누락을 찾으세요.
  • UDP 서비스를 TCP 포트 테스트로 판단DNS·NTP·syslog는 UDP예요. nc -zv(TCP) 결과로는 알 수 없으니 실제 질의로 확인하세요.
🧾실무 팁 (SM 관점)
  • 장애보고서 원인란에 계층과 증거를 함께: "L4 — 8080/TCP timeout(방화벽), ping·경로 정상"
  • 망·보안 담당에게 요청할 땐 출발지·목적지·포트·시각 + 통과한 층까지의 결과 첨부
  • 정기점검 항목에 CLOSE-WAIT 개수 추이 추가 — 연결 누수 조기 발견
  • 시스템 구성도에 장비별 계층(L4 LB, L7 웹서버, WAS)을 표시해 두면 장애 때 동선이 빨라져요
✏️오늘의 퀴즈정답 확인 후 알았음/헷갈림 표시

Q1. ping 정상, nc -zv 8080 timeout. 몇 층 문제이고 누구에게 요청할까?

정답
L4. 포트만 막힌 것 → 방화벽(보안 담당) 확인, 서버의 LISTEN 여부도 함께.

Q2. curl -v에 Connected to 후 HTTP/1.1 504 Gateway Timeout. 무엇부터 볼까?

정답
네트워크는 통과. 뒤의 WAS가 느린 것 → WAS 스레드 덤프, 느린 SQL, 커넥션 풀부터.

Q3. CLOSE-WAIT 연결이 하루 종일 계속 늘어난다. 의심할 것은?

정답
우리 프로그램이 소켓(HTTP·DB 연결)을 닫지 않는 버그. close 누락·try-with-resources 미사용 확인.

Q4. L4 로드밸런서로는 "/api는 A서버, /web은 B서버"로 나눌 수 없는 이유는?

정답
L4는 IP와 포트까지만 봐서 URL(L7 정보)을 모르기 때문. URL별 분배는 L7 장비·웹서버에서.

✍️문제 1쉬움

라우터가 동작하는 OSI 계층은?

정답 2번. 라우터는 IP 주소를 보고 경로를 정하는 네트워크 계층(3계층) 장비예요. 스위치는 MAC을 보는 2계층.
✍️문제 2보통

주로 UDP를 사용하는 프로토콜은?

정답 3번. DNS 조회는 주로 UDP 53번을 써요(응답이 크거나 영역 전송일 땐 TCP). HTTP·FTP·SMTP는 TCP.
✍️문제 3함정

계층과 요소의 연결이 틀린 것은?

정답 3번. MAC 주소는 데이터링크 계층(2계층)이에요. IP 주소(3계층)와 바꿔 내는 함정이 자주 나옵니다.
🌐오늘의 기술 영어로그·문서·에러 메시지에서 자주 보는 표현
Bad Gateway (502)
뒤 서버에서 정상 응답을 못 받음

The proxy returned 502 Bad Gateway because the backend was down.백엔드가 내려가 있어 프록시가 502를 반환했다.
Gateway Timeout (504)
뒤 서버 응답이 시간 초과
📍 웹서버·로드밸런서 응답
Requests over 60 seconds ended with 504 Gateway Timeout.60초를 넘는 요청은 504로 끝났다.
upstream / backend
뒤쪽 서버 (요청을 넘겨받는 WAS 등)
📍 웹서버 설정·에러 로그
Check whether the upstream server is listening on port 8080.뒤쪽 서버가 8080 포트에서 대기 중인지 확인하세요.
Connection reset by peer
상대방이 연결을 강제로 끊음

handshake

OSI 7계층
네트워크 통신을 7단계로 나눈 참조 모델. 실무에선 장애 위치를 나누는 기준으로 씀
TCP/IP 4계층
실제 인터넷이 쓰는 4단계 모델: 네트워크 접근·인터넷·전송·응용
캡슐화 (Encapsulation)
데이터에 계층별 헤더(포트→IP→MAC)를 차례로 붙여 보내는 과정
MAC 주소
랜카드마다 붙은 하드웨어 주소. 같은 네트워크 안에서 전달할 때 사용(L2)
게이트웨이 (Gateway)
다른 네트워크 대역으로 나가는 출구 장비(보통 라우터). ip route의 default via
TCP / UDP
전송 계층 프로토콜. TCP는 연결·순서 보장, UDP는 연결 없이 빠르게(DNS 등)
TIME-WAIT
먼저 연결을 끊은 쪽이 잠시 남겨 두는 정리 대기 상태. 많아도 대개 정상
CLOSE-WAIT
상대가 끊었는데 내 프로그램이 아직 소켓을 안 닫은 상태. 계속 늘면 누수 버그
502 Bad Gateway
앞단(웹서버·프록시)이 뒤(WAS)에서 정상 응답을 못 받았을 때의 HTTP 상태
504 Gateway Timeout
앞단이 기다리는 시간 안에 뒤(WAS)가 응답하지 않았을 때의 HTTP 상태
Bad Gateway (502)
뒤 서버에서 정상 응답을 못 받음 — 웹서버·프록시 응답
Gateway Timeout (504)
뒤 서버 응답이 시간 초과 — 웹서버·로드밸런서 응답
upstream / backend
뒤쪽 서버 (요청을 넘겨받는 WAS 등) — 웹서버 설정·에러 로그
Connection reset by peer
상대방이 연결을 강제로 끊음 — 애플리케이션·네트워크 에러
handshake
연결 수립 과정 (TCP 3-way, TLS) — TLS·네트워크 로그
