📌 ping 실패 ≠ 서버 다운. 보안상 ICMP를 막아 둔 곳이 많아요. 판단은 ② 포트 체크로 합니다.

포트 연결 실패 메시지, 두 가지는 뜻이 완전히 다릅니다

Connection refused
서버까지는 도착했지만 그 포트를 아무도 안 듣고 있음
→ 서비스 미기동·포트 오타 (우리 쪽 확인)
Connection timed out
중간에서 패킷이 버려져 응답 자체가 없음
→ 방화벽 (망/보안팀에 신청)
🔬 심화 — 더 깊이 보기 (+5분)
① TCP 3-way handshake로 보면 차이가 보인다정상: 클라이언트 SYN → 서버 SYN/ACK → 클라이언트 ACK.
닫힌 포트: SYN → 서버가 즉시 RST → refused (바로 실패).
방화벽 DROP: SYN에 아무 응답 없음 → OS가 SYN을 몇 번 재전송하다 포기 → timeout (한참 기다림). 리눅스 기본값이면 2분 가까이 걸릴 수 있어, 앱에는 보통 connect timeout을 짧게 설정합니다.
② 예외: 방화벽인데 refused가 나는 경우방화벽 정책이 DROP(조용히 버림)이 아니라 REJECT(거부 응답)로 설정돼 있으면, 방화벽이 대신 RST나 ICMP 응답을 돌려줘서 바로 실패합니다. "refused = 무조건 서비스 문제"가 아니라, 서버에서 ss -tlnp로 LISTEN 여부를 함께 확인해야 확정할 수 있어요.
③ 방화벽은 보통 3겹 — 어디서 막혔나서버 자체(리눅스 firewalld/iptables, Windows 방화벽) · 네트워크 방화벽(망 구간 장비) · 클라우드 보안그룹. 서버 방화벽만 열고 끝내는 실수가 흔합니다. 서버 안에서 자기 자신으로는 붙는데(curl localhost:8080 OK) 밖에서 안 되면 바깥 두 겹을 의심하세요.
# 서버 방화벽 규칙 확인 (RHEL/Rocky 계열)
firewall-cmd --list-all
# iptables 직접 사용 환경
iptables -L -n --line-numbers
④ 리뷰·면접에서 나오는 질문Q. ping은 되는데 포트 연결이 안 되는 원인 3가지?
A. ① 서비스 미기동(LISTEN 없음) ② 127.0.0.1에만 바인딩 ③ 해당 포트만 방화벽 차단. — ping(ICMP)과 TCP 포트는 별개로 허용·차단된다는 점이 핵심.
🪟실습 1 · Windows에서 포트 확인
# 포트 연결 테스트 (telnet 없어도 OK)
Test-NetConnection 192.0.2.10 -Port 8080
# 축약형
tnc 192.0.2.10 -p 8080
▶ 이렇게 나오면
WARNING: TCP connect to (192.0.2.10 : 8080) failed
ComputerName     : 192.0.2.10
RemoteAddress    : 192.0.2.10
RemotePort       : 8080
SourceAddress    : 192.0.2.11
PingSucceeded    : True
TcpTestSucceeded : False
🔎 결과 읽는 법
  • TcpTestSucceeded : True면 포트 열림, False면 막힘 또는 미기동
  • PingSucceeded : True + TCP False → 길은 있는데 그 포트만 문제
  • 결과가 즉시 나오면 refused 쪽, 20초 이상 걸리면 방화벽(timeout) 쪽일 가능성이 큼
  • SourceAddress가 방화벽 신청서의 출발지 IP예요
🐧실습 2 · Linux에서 상대 포트 확인
# 3초만 기다리고 결과 보기
nc -zv -w 3 192.0.2.10 8080
# nc가 없을 때
timeout 3 bash -c '</dev/tcp/192.0.2.10/8080' \
  && echo OPEN || echo FAIL
# 응답 헤더까지 확인
curl -v --connect-timeout 3 http://192.0.2.10:8080/
▶ 이렇게 나오면
# 성공
Connection to 192.0.2.10 8080 port [tcp/http-alt] succeeded!
# 서비스 미기동
nc: connect to 192.0.2.10 port 8080 (tcp) failed: Connection refused
# 방화벽 의심
nc: connect to 192.0.2.10 port 8080 (tcp) timed out: Operation now in progress
🔎 결과 읽는 법
  • 메시지 끝의 refused / timed out만 보면 어느 쪽인지 바로 갈려요
  • RHEL 계열의 ncat은 Ncat: Connection refused., Ncat: TIMEOUT.처럼 표시돼요
  • curl -v에서 Connected to가 찍혔다면 네트워크는 통과 → 이후 HTTP 상태코드(404, 500)는 애플리케이션 문제
🖥️실습 3 · 서버에서 LISTEN 확인
# 어떤 프로세스가 어떤 주소:포트로 대기 중인가
ss -tlnp | grep 8080
# 구버전 서버
netstat -tlnp | grep 8080
▶ 이렇게 나오면
State  Recv-Q Send-Q Local Address:Port Peer Address:Port Process
LISTEN 0      100          0.0.0.0:8080      0.0.0.0:*   users:(("java",pid=2310,fd=45))
🔎 결과 읽는 법
  • 아무것도 안 나오면 서비스가 안 떠 있거나 포트가 다름 → 기동 로그 확인
  • Local Address가 0.0.0.0(또는 *, [::])이면 외부 접속 가능, 127.0.0.1이면 서버 내부만
  • Process의 pid로 어떤 프로그램인지 확인 → ps -fp 2310
  • -p(프로세스 표시)는 root 권한이 있어야 다른 사용자 프로세스까지 보여요
⚠️흔한 실수현장에서 실제로 자주 나오는 것
  • ping 실패만 보고 "서버 다운"이라고 보고ICMP 차단은 흔합니다. 판단은 반드시 포트 연결 테스트로 하고, 보고에는 어떤 테스트로 확인했는지 함께 적으세요.
  • 서버 방화벽만 열고 "조치 완료"중간 네트워크 방화벽·보안그룹은 별도 신청입니다. 실제 호출하는 서버에서 다시 테스트해 보고 완료 처리하세요.
  • 방화벽 신청서에 내 PC IP를 출발지로 적음출발지는 실제로 호출하는 서버(WAS)의 IP입니다. 중간에 NAT가 있으면 변환된 IP가 기준이니 망 담당자에게 확인하세요.
  • localhost로만 테스트하고 OK서버 안에서 curl localhost가 되는 건 서비스가 떠 있다는 뜻일 뿐, 외부 접근은 바인딩 주소와 방화벽을 따로 확인해야 해요.

  • 신청 전 timeout 결과를 캡처해 두면 처리가 빨라요

✏️오늘의 퀴즈정답 확인 후 알았음/헷갈림 표시

Q1. ping은 실패, Test-NetConnection -Port 443은 성공. 서버 상태는?

정답
정상. ICMP만 막혀 있고 443 서비스는 살아 있음.

Q2. Connection refused. 방화벽 신청부터 해야 할까?

정답
아니요. 서버까지는 도달 → 서비스 기동 여부·포트 번호부터 확인.

Q3. 127.0.0.1:9090 LISTEN. 다른 서버에서 붙을 수 있을까?

정답
불가. 루프백에만 바인딩 → 바인드 주소를 0.0.0.0(또는 서버 IP)으로 변경.

Q4. Test-NetConnection이 False인데 결과가 30초 뒤에 나왔다. 무엇을 먼저 의심할까?

정답
방화벽(DROP)에 의한 timeout 가능성. 즉시 실패였다면 서비스 미기동(refused) 쪽을 먼저 봅니다.

오늘 개발공부의 refused / timeout 차이가 문제 2번의 실무 버전이에요.
✍️문제 1쉬움

TCP 3-way handshake의 순서로 옳은 것은?

정답 1번. 클라이언트가 SYN으로 요청 → 서버가 SYN/ACK로 응답 → 클라이언트가 ACK로 확인하면 연결이 수립됩니다. FIN은 연결 종료(4-way)에 쓰여요.
✍️문제 2보통

클라이언트가 SYN을 보냈지만 해당 포트에서 대기 중인 프로세스가 없을 때, 서버가 돌려보내는 플래그는?

정답 3번. 닫힌 포트로 SYN이 오면 RST로 응답 → 클라이언트에는 Connection refused. 방화벽이 패킷을 버리면 응답이 없어 timeout이 됩니다.
✍️문제 3함정

잘 알려진 포트(well-known port)와 서비스의 연결이 틀린 것은?

정답 4번. 110은 POP3(메일 수신)이고, SMTP(메일 발송)는 25번입니다. 메일 관련 포트(25/110/143)는 서로 바꿔 내는 함정이 자주 나와요.

근본 원인 예외. Caused by 줄이 진짜 원인을 알려줘요
Connect timed out
연결 단계에서 시간 초과 → 방화벽·경로 문제 의심
💡 Connect timed out(연결 자체가 안 됨 → 네트워크)과 Read timed out(연결은 됐는데 응답이 늦음 → 상대 서버 처리 지연)은 원인이 완전히 달라요. 로그에서 이 두 단어부터 구분하세요.
포트 (Port)
한 서버 안에서 어떤 서비스로 갈지 구분하는 번호. 예: 80(HTTP), 443(HTTPS), 8080(WAS)
ICMP
ping이 사용하는 프로토콜. 보안상 차단된 경우가 많아 ping 실패 ≠ 서버 다운
Connection refused
서버에는 도달했지만 해당 포트에서 듣는 프로세스가 없음
Connection timed out
응답이 아예 없음. 중간 방화벽에서 패킷이 버려지는 경우가 대부분
LISTEN
프로세스가 특정 포트에서 연결을 기다리는 상태 (ss -tlnp로 확인)
루프백 (127.0.0.1)
자기 자신을 가리키는 주소. 여기에만 바인딩하면 외부 접속 불가
0.0.0.0 바인딩
서버의 모든 네트워크 인터페이스에서 연결을 받겠다는 뜻
3-way handshake
TCP 연결 수립 과정. SYN → SYN/ACK → ACK
RST
TCP 연결을 즉시 끊거나 거부할 때 보내는 플래그. 닫힌 포트에 연결하면 RST가 와서 refused가 됨
DROP / REJECT
방화벽 차단 방식. DROP은 응답 없이 버림(→timeout), REJECT는 거부 응답을 보냄(→즉시 실패)
보안그룹 (Security Group)
클라우드에서 서버 단위로 적용하는 가상 방화벽 규칙
Connection refused
연결 거부됨 — curl·애플리케이션 에러 메시지
timed out
시간 초과 — 네트워크·DB 연결 에러
listen on / bind to
(포트에서) 대기하다 / (주소에) 바인딩하다 — 서버 설정 문서·기동 로그
inbound / outbound rule
들어오는 / 나가는 방화벽 규칙 — 방화벽·클라우드 보안 설정
Destination host unreachable
대상 호스트에 도달할 수 없음 — ping 결과 메시지
