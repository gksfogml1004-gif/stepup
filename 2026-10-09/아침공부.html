📌 산출물은 "제대로 했다"는 증거입니다. 문제가 생겼을 때 누가·언제·무엇을·왜 바꿨는지 추적할 수 있게 해 줍니다. 소스 변경 이력은 형상관리(Git/SVN)로 함께 남깁니다.

산출물은 크게 두 종류로 나뉩니다

수시 산출물 — 건마다
요청서 · 영향도 분석서 · 테스트 결과서 · 이행계획서 · 작업결과서 · 장애보고서(장애 발생 시)
정기 산출물 — 주기마다
월간 운영보고서(처리 건수, SLA 지표, 장애 현황) · 정기점검 결과 · 백업·보안 점검 결과
🔬 심화 — 더 깊이 보기 (+5분)
① 추적성(Traceability) — 산출물이 서로 이어져야 한다요청번호 하나로 요청서 → 커밋 → 배포 파일 목록 → 작업결과서가 줄줄이 찾아져야 합니다. 점검·감사 때 확인하는 것도 결국 "이 변경이 승인된 요청에서 나왔고, 테스트를 거쳐, 기록대로 반영됐나"예요. 문서가 따로 놀면(요청서엔 3본, 배포엔 5본) 바로 지적 대상입니다.
② 긴급 변경 — 승인보다 조치가 먼저일 때장애로 즉시 반영이 필요하면 구두·메신저 승인으로 먼저 조치하고, 사후에 요청서·결과서를 작성해 정식 승인을 받습니다(긴급 변경 절차). 이때 누가 언제 승인했는지와 긴급 사유를 반드시 남기세요. 사후 문서가 빠지면 월간 보고·점검에서 '무단 변경'으로 보입니다.
③ 문서는 최신화가 생명운영 중 변경이 설계서·프로그램 목록·테이블 정의서에 반영되지 않으면 다음 담당자가 문서를 믿을 수 없게 됩니다. 변경 1건이 끝날 때 "이번 변경으로 바뀐 문서"를 체크하는 습관이 인수인계 품질을 결정해요.
④ 리뷰·면접에서 나오는 질문Q. 영향도 분석을 어떻게 하나요?
A. 변경 대상(프로그램·테이블)의 호출처를 소스 검색으로 뽑고, 화면·배치·연계·데이터·운영 관점으로 영향 여부를 판단해 근거와 함께 기록합니다. 그 결과가 테스트 범위가 됩니다.
🧩영향도 분석 — 이것만은 체크
  • 화면·기능: 수정 프로그램을 호출하는 다른 화면/배치가 있나
  • DB: 테이블·컬럼 변경 시 같은 테이블을 쓰는 쿼리·뷰·프로시저
  • 연계: 외부 기관·타 시스템 인터페이스에 영향이 있나
  • 데이터: 기존 데이터 보정(마이그레이션)이 필요한가
  • 운영: 서비스 중단 필요 여부, 작업 시간대
💡 영향 범위를 찾을 땐 소스 전체에서 grep -rn "프로그램ID 또는 테이블명"으로 호출처를 먼저 뽑아 보세요.
🔗요청번호로 변경 추적하기 (Git)
# 요청번호가 들어간 커밋 찾기
git log --oneline --grep="SR-2026-0001"
# 그 커밋에서 바뀐 파일 목록
git show --stat --oneline a1b2c3d

🔎 결과 읽는 법
  • 커밋 메시지에 요청번호가 있어야 이 검색이 됩니다 → 커밋 규칙이 곧 추적성
  • --stat 결과가 그대로 배포 파일 목록·작업결과서의 '대상'이 돼요
  • SVN이라면 svn log --search "SR-2026-0001"(1.8 이상)로 같은 일을 할 수 있어요

작업자/확인자 : 담당 개발자 / 고객 담당자

↩️이행계획서 — 롤백 계획 예시
# 롤백 계획
판단 기준 : 배포 후 30분 내 주요 화면 오류 또는
           에러 로그 급증 시 즉시 롤백
롤백 대상 : order-web.war (배포 전 버전)
백업 위치 : /app/backup/20261009/
롤백 절차 : ① WAS 중지 → ② 백업 파일 복원
           ③ WAS 기동 → ④ 주요 화면 확인
예상 소요 : 10분
연락 체계 : 작업자 → PM → 고객 담당자
💡 롤백은 판단 기준이 핵심이에요. "문제가 생기면"이 아니라 "무엇이 보이면, 몇 분 안에"로 적어야 현장에서 망설이지 않습니다.
⚠️흔한 실수현장에서 실제로 자주 나오는 것
  • 작업 끝나고 문서를 몰아서 작성기억에 의존하게 되고 증거(캡처·로그)가 빠집니다. 작업 중에 바로 캡처하고, 결과서는 당일에 마무리하세요.
  • 영향도 분석에 "영향 없음" 한 줄무엇을 확인해서 없다고 판단했는지(검색 결과, 호출 목록)를 남겨야 나중에 문제가 생겨도 설명할 수 있어요.
  • 긴급 조치 후 사후 문서 누락급하게 고치고 나면 잊기 쉽습니다. 조치 직후 요청서·결과서 작성 일정을 바로 잡아두세요.
🧾실무 팁 (SM 관점)
  • 이행계획서에 롤백 절차와 "언제 롤백을 결정하는지" 기준을 꼭 적기
  • 요청번호(SR)를 커밋 메시지·작업결과서·배포 목록에 똑같이 남기면 추적이 쉬워요
  • 테스트 결과서는 "성공"만이 아니라 입력값·기대값·실제값을 남기기
  • 어제 배운 방화벽 확인 캡처처럼, 작업 전/후 화면은 그때그때 저장
✏️오늘의 퀴즈정답 확인 후 알았음/헷갈림 표시

Q1. 개발에 들어가기 전, 변경이 다른 화면·배치·연계에 미치는 범위를 정리하는 문서는?

정답
영향도 분석서. 테스트 범위도 여기서 정해집니다.

Q2. 이행계획서에서 자주 빠지지만 장애 때 가장 중요한 항목은?

정답
롤백(원복) 절차와 판단 기준. 원래 파일 백업 위치, 원복 순서, 소요 시간까지.

Q3. 월간 운영보고서에 들어가는 SLA 지표의 예를 두 가지 들어 보세요.

정답
요청 처리기한 준수율, 장애 복구 시간, 서비스 가용률 등.

Q4. 장애로 승인 전에 먼저 반영했다. 산출물은 어떻게 처리할까?

정답
긴급 변경 절차로 사후에 요청서·결과서를 작성해 승인받고, 승인자·시각·긴급 사유를 기록합니다.
🚨장애 케이스 스터디 — 주말 지나고 "화면이 안 열려요"가상의 일반 사례
증상월요일 아침, 사용자들이 "화면이 하얗게 나와요"라고 연락. WAS 프로세스는 살아 있다.
  1. ① 확인 — 디스크부터프로세스가 살아 있는데 응답이 이상하면 디스크·메모리를 먼저 봅니다.
    df -h
# /app 파티션 Use% 100%
  2. ② 범인 찾기어떤 파일이 공간을 차지하는지 확인.
    du -sh /app/logs/* | sort -h | tail -5
  3. ③ 원인운영에 DEBUG 로그 레벨로 배포 + 로그 정리 설정 없음 → 주말 동안 로그 급증.
  4. ④ 조치오래된 로그 압축·이동으로 공간 확보 → 로그 레벨 INFO로 변경 후 재기동 → 화면 확인.
  5. ⑤ 재발 방지로그 롤링(일자·용량 기준) 적용, 디스크 사용률 80% 경고 알람 추가.

📝 장애보고서에는 이렇게

원인: 운영 환경 로그 레벨이 DEBUG로 설정되어 로그가 급증, /app 파티션 사용률 100% 도달 → 파일 쓰기 실패로 화면 응답 오류
조치: 로그 정리 및 로그 레벨 INFO 변경 후 WAS 재기동 (09:40 정상화)
재발방지: 로그 롤링 정책 적용, 디스크 사용률 80% 알람 추가
⚠️ 프로세스가 쓰고 있는 로그 파일을 rm으로 지우면 공간이 바로 돌아오지 않을 수 있어요. 비울 땐 > 파일명(내용만 비우기)을 쓰거나, 삭제 후 해당 프로세스를 재기동합니다.

수정(Corrective)발견된 오류 수정
적응(Adaptive)OS·DB 등 환경 변화 대응
완전화(Perfective)기능 추가·성능 개선
예방(Preventive)미래 문제 예방
형상관리 도구
중앙 집중형: CVS, SVN · 분산형: Git
출제 경향을 참고해 만든 연습 문제예요. 시험 일정·제도는 공식 사이트에서 확인하세요.
SM 업무 대부분이 '수정·적응·완전화' 유지보수예요. 요청서에 유형을 구분해 두면 월간 보고 통계가 쉬워집니다.
✍️문제 1쉬움

운영 중 발견된 프로그램 오류를 고치는 유지보수 유형은?

정답 1번. 오류를 바로잡는 것은 수정(Corrective). OS·DB 버전업 대응은 적응, 기능 개선은 완전화, 미래 문제 예방은 예방 유지보수입니다.
✍️문제 2보통

소프트웨어 형상관리(SCM)의 주요 활동에 해당하지 않는 것은?

정답 4번. 주요 활동은 식별·통제·감사·기록(상태 보고)입니다. '형상 개발'이라는 활동은 없어요. 변경요청 승인 절차가 '통제', 커밋 이력 관리가 '기록'에 해당합니다.
✍️문제 3함정

다음 중 분산형 형상관리(버전 관리) 도구는?

정답 3번. Git은 각 개발자 PC에 전체 저장소 이력을 두는 분산형입니다. CVS·SVN은 중앙 서버에 저장하는 중앙 집중형, RCS는 개별 파일 단위의 오래된 도구예요.

📄독해 연습 — 영문 장애 보고서 요약 읽기먼저 스스로 읽고 해석을 펼쳐 보세요
Incident Summary
Impact: Users could not load the order page (09:00-09:40).
Root cause: Disk usage on /app reached 100% due to excessive DEBUG logging.
Resolution: Old logs were archived and the log level was changed to INFO.
Action items: Enable log rotation; add an alert at 80% disk usage.

산출물
사업·운영 과정에서 작성해 남기는 문서와 결과물. 작업을 제대로 했다는 증거이자 추적 근거
SR (Service Request)
서비스 요청. 변경·개선·문의 등 운영 요청 1건을 식별하는 단위로 요청번호를 붙여 관리
영향도 분석
변경이 다른 화면·배치·DB·연계 시스템에 미치는 범위를 미리 파악하는 작업
이행 (배포)
개발·테스트가 끝난 변경을 운영 환경에 반영하는 작업
롤백 (Rollback)
반영한 변경에 문제가 생겼을 때 이전 상태로 되돌리는 것
형상관리
소스·문서의 버전과 변경 이력을 관리하는 것 (Git, SVN 등)
SLA
서비스 수준 협약. 처리기한, 복구 시간, 가용률 등 지켜야 할 서비스 수준을 수치로 정한 약속
작업결과서
운영 작업의 일시·대상·내용·확인 결과를 기록한 문서
로그 롤링
로그 파일을 날짜·용량 기준으로 나누고 오래된 파일을 정리하는 설정
추적성 (Traceability)
요청 → 소스 변경 → 배포 → 결과 기록이 서로 연결되어 거슬러 찾아갈 수 있는 성질
긴급 변경

감리
